   local `SecureStorage`/`SecureStorageData` mirrors copied from the
   established `fallbackStorage.ts` mirror (which cites
   `src/shared/utils/secureStorage/types.ts` as the eventual contract).
3. `shared/utils/settings/validation.ts` — `ConfigScope` import repointed
   `src/services/mcp/types.js` → `src/runtime/services/mcp/types.js`; the
   former is a legacy shim without `ConfigScope` (where `ConfigScopeSchema`
   actually lives). Type-only import, erased at runtime.
4. `runtime/tools/builtins/registry.ts` — `ToolContext`/`ToolDefinition`
   moved to the `@allternit/plugin/tool` subpath (package root
   `index.ts` never re-exported `tool.ts`; the `./tool` export map entry
   exists). Hook name `"tool.definition"` cast `as any` per the
   established `"shell.env"` precedent (bash.ts, pty/index.ts).
5. `runtime/session/llm.ts` — hook names `"experimental.chat.system.transform"`
   and `"chat.params"` cast `as any`, same precedent.
6. `utils/caCerts.ts` — `getCACertificates.cache.clear?.()` (lodash-es

   void } }` (first-iteration direct cast hit TS2352 insufficient-overlap,
   went through `unknown`).

### Noted for follow-up (not escalated, no behavior change)

The plugin SDK (`packages/plugin/src/tool.ts`) declares
`ToolDefinition.execute()` returning `string | { output; title?; metadata? }`,
but `registry.ts fromPlugin()` has always passed the raw result to
`Truncate.output(string)` and returned it as `output: string`. The burn
preserves that exact behavior via `result as string` casts. If the SDK's
object form is ever exercised by a real plugin, `Truncate.output` receives
an object — pre-existing since before the nocheck header, now visible in
the types. A future lane could normalize the object form in `fromPlugin`.
