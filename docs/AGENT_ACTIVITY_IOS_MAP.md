# Agent Activity — iOS Phase 1 Map

Third and final planned phase's first step (web → **iOS** → gizzi-code CLI) of the same initiative as `docs/AGENT_ACTIVITY_WEB_MAP.md` / `docs/AGENT_ACTIVITY_WEB_PHASE_1_NOTES.md` (merged, PR #17). Read both — the web phase is the reference design (`docs/agent-activity-design/mockup-v3.html`) and, importantly, documents real backend gaps already found so this phase doesn't have to rediscover them.

## Backend: same `allternit-api` Rails Mail system, verified directly (not copied from web's own workaround)

Mounted at `/rails` **and** `/api/rails` (`cmd/allternit-api/src/main.rs:330-331`, inside the Clerk-authenticated "protected" router group — same auth as every other allternit-api endpoint iOS already calls). Real handlers read directly from `cmd/allternit-api/src/rails/mod.rs`:

- **`GET /api/rails/mail/threads`** (`list_mail_threads`, line 843) → `{ threads: [{ thread_id, messages: <count:Int>, last_ts: <ISO8601 string> }] }`. **Use this — do not replicate web's `fetchMailThreads` workaround.** Web's own store derives threads client-side from individual messages instead of calling this real endpoint (a documented, filed gap — issue #16). This real endpoint already exists, is correct, and iOS should just use it directly. `messages` is a count, not the list — no message bodies here.
- **`GET /api/rails/mail/thread/:thread_id`** (`read_mail_thread`, line 877) → `{ messages: [{ message_id, thread_id, from_agent, body, event_type, timestamp }] }`. `body` may be a JSON value, not always a plain string — decode leniently (a string when present; treat other JSON shapes as "no plain-text body" rather than crashing).
- **`POST /api/rails/mail/send`** (line 620) — body `{ thread: <topic-or-thread-id-string>, body: <string> }` is sufficient for a human reply (the richer `from_agent`/`to_agents`/`subject`/`importance` fields are for the agent-to-agent envelope path, not needed here) → `{ sent, thread_id, message_id }`.
- **`POST /api/rails/mail/decide`** (line 995) — body `{ thread, approve: <bool> }` (server also accepts a `decision` string, but `approve` is simpler and sufficient — `MailDecideRequest`, resolves to `"accepted"`/`"rejected"` either way, strictly boolean, no N-way decisions) → `{ decided, thread_id }`.
- **`POST /api/rails/mail/share`** (line 922) — body `{ thread, asset_ref: <string>, note?: <string> }` → `{ shared, share_id, thread_id }`.
- **`POST /api/rails/ledger/tail`** (`railsApi.ledger.tail` on web, `unified.store.ts:1161` — real, working, already proven) — body `{ count: <int> }` → `LedgerEvent[]` (each roughly `{ event_id, event_type, ts, actor, payload, scope? }`, `payload` untyped JSON). This is the real mechanism for reservation/guard visibility: fetch a batch, filter client-side where `payload.thread_id == threadId || payload.mail_thread_id == threadId`, same heuristic web's `AGENT_ACTIVITY_WEB_PHASE_1_NOTES.md` already documents (substring match on `event_type` against `/guard/i`/`/reserve/i`/`/review/i`/`/decide/i` — there is no documented `event_type` vocabulary, this is read-only best-effort surfacing, not a guaranteed status field).

## iOS conventions to reuse

- **Base URL derivation**: `AppConfig.swift` already has the exact precedent needed — `agentChatURL` and `aciBaseURL` (lines ~20-44) both strip a trailing `v1` path component from `apiBaseURL` (`http://host/api/v1` → `http://host/api`) then append the real mount name, because those two routers are also mounted directly under `/api`, not nested under `/api/v1`. Add `railsBaseURL` the identical way, appending `"rails"`.
- **Client shape**: `Core/API/ProjectsClient.swift` — wraps `APIClient.shared` (Clerk Bearer auth, relay-aware), `client.get/post(path:)`/`client.get/post(path:body:)`. Since rails endpoints live at an absolute URL outside `apiBaseURL`'s path space (same situation `agentChatURL`/`aciBaseURL` already solve), build requests the way those are consumed elsewhere in this codebase — check how `agentChatURL`/`aciBaseURL` themselves get used for the exact request-building idiom (probably `APIClient.shared.authorizedRequest(url:method:)` + manual `session.data(for:)`, matching `RuntimeDevicesClient`'s pattern for its own out-of-`apiBaseURL` cloud-API calls — verify by reading, don't assume the two idioms are identical).
- **List/detail UI**: `Features/Projects/Views/ProjectsListView.swift` + `ProjectDetailView.swift`, and the more recently-built `Features/Automation/Views/AutomationTasksListView.swift` + detail view (same app, same session, most current precedent) — list → tap → **push** to detail (SwiftUI's native `NavigationStack`/`.navigationDestination`, not a `.sheet`). This is iOS's natural non-modal equivalent of the web phase's "real route, not a panel" fix — a pushed detail view already isn't a modal, so this constraint is satisfied by using normal navigation, not by inventing anything new.
- **Store pattern**: `Core/CronJobStore.swift` / `Core/CoworkTasksStore.swift` — `@MainActor final class ... ObservableObject`, `static let shared`, `@Published` state, `refresh()`/mutation methods.

## Scope decision

Phase 1: thread list (real `/mail/threads`, Tasks-list-style row: topic — note real threads' `topic` is presently just the `thread_id` string per web's own finding, there is no separate human title yet, display it as-is — unread heuristic, review/guard/reservation tags), thread detail (message history, typed review card using the same boolean-`decide()` semantics as the web phase, Approve/Reject, reply box, Share), reservation/guard visibility (read-only, ledger-tail-derived, same heuristic as web). Entry point: a new item in wherever this app's existing utility/settings-adjacent entry points live (check `ComposerPlusSheet.swift` — used for Cowork Tasks' own entry point this same session — or a tab, your call based on what fits; unlike Automation Tasks this isn't inherently a top-level "mode," it's cross-cutting notification-style content, so a lighter entry point than a new `ModeBarItem` case is probably right, but verify against how this app already surfaces cross-cutting things like Connectors or Brain capture before deciding).

Not in scope: archive (web's own phase found this maps to a confusing, not-actually-"hide"-semantics server call with only a client-side-tracked UI state — defer until product clarifies intent, don't replicate a workaround of a workaround), gizzi-code CLI phase (separate, later).
