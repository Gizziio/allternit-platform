# BYOC / Desktop-Cloud-iOS Backend Architecture Audit

**Date:** 2026-08-05
**Status:** AUDIT COMPLETE, on-device feasibility VERIFIED — decoupling + local-model-hosting work not yet started
**Trigger:** iOS request to add open-source/local model hosting (inspired by PocketPal AI) surfaced a bigger question — does the backend cleanly support desktop, cloud-hosted, and iOS surfaces off one shared core, and is that the right long-term shape?

---

## Executive Summary

**The short answer: yes, mostly already.** Allternit already built the architecture that companies use for this exact problem — a thin cloud control plane, a data plane that runs on whatever compute the user has (their desktop, a VPS, or a cloud-hosted container), and an outbound-only relay connecting them so no inbound firewall holes are needed. This is the same shape used by BYOC infra vendors (Confluent, RisingWave, Twingate) and remote-dev platforms (Gitpod/Ona). iOS is already a first-class client of it (`RuntimePairing.swift`, `InstancesClient.swift`).

The gaps are **not architectural** — they're a handful of un-reconciled edges where a genuinely shared design has drifted apart in practice: a binary not vendored into one deployment target, two independent implementations of the same bootstrap logic, an escape hatch that exists but isn't wired up. All are decouple-don't-delete fixes, not rewrites.

Open-source/local model hosting (the original ask) should be built as a **capability of the existing runtime/relay system**, not a new subsystem — see [Where Local Model Hosting Fits](#where-local-model-hosting-fits).

---

## The Target Pattern (why this is "the correct way")

Industry-standard BYOC shape, confirmed against current (2026) practice at Confluent/RisingWave/Twingate/BentoML and Gitpod/Ona's remote-workspace architecture:

```
 ┌─────────────┐        outbound-only WS         ┌──────────────────────┐
 │  Data Plane  │ ───────────────────────────────▶│    Control Plane      │
 │ (user compute)│◀─────────────────────────────── │  (cloud, thin, vendor) │
 └─────────────┘         relayed requests          └──────────────────────┘
        ▲                                                     ▲
        │ same code, wherever it runs                         │ auth, pairing,
        │ (desktop / VPS / hosted container)                  │ capability routing
        │                                                     │
   user's own machine                                    thin clients
   or a rented cloud box                                (iOS, web, CLI)
```

- **Control plane** (vendor-managed): pairing/auth, capability routing, relay. Never touches the user's model weights, provider keys, or local files.
- **Data plane** (user/customer-managed): where inference and execution actually happen. Same binary/process regardless of *where* it's deployed.
- **Outbound-only agent**: the data-plane side always dials out to the control plane — never the reverse — so it works behind arbitrary NATs/firewalls with zero inbound config.
- **Capability negotiation, not platform forking**: instead of separate "desktop backend" vs "iOS backend" codebases, one core exposes a capability list; each deployment target (desktop/VPS/hosted) advertises which capabilities it actually has (terminal access, local GPU, etc.), and clients render around what's available.

**Allternit's current implementation of this pattern:**

| Piece | Role | File(s) |
|---|---|---|
| Control plane | Pairing, auth, relay, capability-scoped socket tickets | `cmd/allternit-cloud-api/src/routes/runtime_pairing.rs`, `runtime_relay.rs` |
| Data-plane client | Outbound-only relay agent, identical on desktop/VPS/hosted | `cmd/agent-daemon/src/index.ts` |
| Data-plane core | Model/harness execution | `cmd/gizzi-code` (`serve`), proxied to by agent-daemon at `LOCAL_GATEWAY_URL` |
| Thin client (already wired) | Pairs itself as an `ios` runtime type, lists paired compute | `surfaces/allternit-mobile/ios/Core/Auth/RuntimePairing.swift`, `InstancesClient.swift` |
| Local-vs-remote dual implementation (existing precedent) | `trait Runtime { start/stop/status/attach/exec }`, impl'd by `local_runtime.rs` (on-box VM) and `remote_runtime.rs` (SSH) | `cmd/allternit-cloud-api/src/runtime/mod.rs` |

This is a real, working system — `runtime_pairing.rs`/`runtime_relay.rs` total ~2400 lines with zero `TODO!`/`unimplemented!` markers, not a scaffold. **The frame going into this doc — "can we even do BYOC on iOS without deleting desktop features" — has a concrete existing answer: yes, and it's mostly already built.** What's below is what's still rough at the edges.

## Verified Findings: Decoupled vs. Tangled

### ✅ Genuinely decoupled / platform-neutral today

- **`agent-daemon`** — no Electron IPC, no desktop-specific branching anywhere in its ~450 lines. Identical code runs on desktop, VPS, and the hosted-runtime container. This is the reference example for what "decoupled" looks like in this codebase.
- **The pairing/relay protocol** (`runtime_pairing.rs`, `runtime_relay.rs`) — mature, capability-scoped (`runtime:terminal`, `providers:use`, etc., enforced both client- and server-side), already consumed by iOS.
- **`Runtime` trait** (Cowork) and **`ExecutionDriver` trait** (`initialize_vm_driver()` in `cmd/allternit-api/src/main.rs:707-745`, `#[cfg(target_os = "linux")]` → Firecracker, `#[cfg(target_os = "macos")]` → Apple VF) — both are working local/remote or platform-gated dual-implementation examples already in the codebase. Reuse these patterns rather than inventing a new one.
- **Sidecar's env-var escape hatches** (`ALLTERNIT_SIDECAR_URL` to point at a remote inference server, `ALLTERNIT_SIDECAR_DISABLED=1` to skip local auto-spawn) — the right pattern, just not wired into every deployment target yet (see below).

### 🚧 Tangled today — concrete, scoped fixes, none requiring deletion

1. **`allternit-mux` isn't vendored into `allternit-hosted-runtime`.** It's a Unix-socket daemon (`~/.allternit/mux/mux.sock`), auto-spawned by gizzi-code itself (`src/runtime/integrations/pty/index.ts`) wherever gizzi-code runs — the protocol is already location-agnostic (same-machine-only by design, which is correct for a PTY). But the hosted-runtime `Dockerfile`/`entrypoint.sh` never builds or copies the binary in, so **cloud-hosted terminal/PTY features are silently dead today** — not an architecture problem, a missing build step. *Fix: cross-compile + vendor the Linux binary into the hosted-runtime image.*

Last touched 2026-07-16.
   **But it's completely unwired**: grepped every file in `surfaces/ai.allternit.com/src` for an import of anything under `local-models/` from outside that directory — zero hits. `registerDefaultLocalProviders()` (the one function that activates all four providers) is never called anywhere in the live app. This is real, working-looking, substantial code with no current integration, not dead code and not live code — a third state distinct from both.
   **Resolved 2026-08-05 (Eoj decision): not using Bonsai.** Recommendations #1-4 stand as originally scoped — generalize gizzi-code's Sidecar (not Bonsai) for the desktop/VPS/cloud-hosted tier, and the on-device Swift harness's engine choice (#16) is back to an open question rather than settled by Bonsai precedent. Bonsai itself is left as-is (unwired, not deleted) — out of scope for this work.

None of these require touching, deleting, or forking any desktop-only feature. Every one is a build/deploy/config gap, not a code-architecture gap.

## Where Local Model Hosting Fits

Given the pattern above, open-source/local model hosting (the original PocketPal-inspired ask) is a **capability of the data plane** (wherever gizzi-code runs), advertised through the existing capability-scoped relay — not a new subsystem, and not something that runs inside the iOS process itself.

**Why not on-device-in-the-iOS-app (PocketPal's actual approach):** `allternit-api` never calls a model provider directly — every model call, cloud or local, already goes through gizzi-code over HTTP. Baking a second, parallel inference path directly into the iOS binary would bypass the harness entirely, which is exactly what Eoj flagged as wrong. The harness-routing requirement is the reason this is a backend capability, not an iOS feature.

**What already exists to build on:** gizzi-code's `Sidecar` module (`src/runtime/sidecar/`) already does "ship a quantized GGUF-class model, auto-download on first run, run it locally, expose as an Ollama-compatible provider" — today hardcoded to one model (Qwen 3.5 4B) for internal use only (title-gen, compaction). `discovery/local.ts` + the `Provider.Info` abstraction (`auth_type: "none"` slot) already handle registering any local OpenAI-compatible server as a user-facing provider.

**Built 2026-08-05 (recommendations #1-3 implemented, verified compiling both sides):** Sidecar generalized (`cmd/gizzi-code/src/runtime/sidecar/index.ts`) — `searchHuggingFace()` (HF's public model-search API filtered to `gguf`), `installCustomModel()`/`removeModel()` (pull/remove via Ollama's own `hf.co/<repo>[:<quant>]` support — gizzi-code never touches raw weights or parses GGUF itself), `listInstalledModels()`, and `providerConfig()` now async and includes every installed model, not just the embedded default. `cmd/allternit-api/src/v1_routes.rs`'s `GET /api/v1/models` — previously a **static, compile-time-only catalog** (`CLI_PROVIDER_SPECS`/`ENV_PROVIDER_SPECS` Rust constants, a real gap discovered while implementing: it could never have surfaced runtime-installed local models regardless of what the harness reported) — now merges in gizzi-code's live `GET /provider` `connected` list on top of the static entries, with a 3s timeout and graceful fallback if gizzi is unreachable. Recommendation #3 (relay capability advertisement) scoped down: the core goal (local models usable from iOS once connected) is already satisfied by the catalog fix above; a "which paired runtime has local models before you connect" discovery nicety would need a live-status mechanism `agent-daemon`'s pairing-time capability list doesn't support (capabilities are set once at pairing, local model sets change afterward) — not built, flagged as a real but separate follow-up if wanted. `tsc --noEmit` and `cargo check -p allternit-api` both clean.

**Correction (2026-08-05, after Eoj review):** an earlier draft of this doc deferred true on-device (in-process, iPhone-local) inference as out of scope, reasoning that the harness only runs where gizzi-code runs (desktop/VPS/cloud). Eoj's pushback is correct and changes the design: hosting local models *only* on the desktop backend means no model availability at all when the desktop isn't running, capped at desktop RAM/GPU. Real on-device hosting is wanted — but it must still go through "an intelligent harness," not be a bare llama.cpp chat loop bolted onto the iOS app. Both constraints are satisfiable together — see the fourth tier below.

**Recommended phased approach:**

1. **Generalize Sidecar beyond one fixed model** — arbitrary GGUF selection + HuggingFace search/download (the actual PocketPal parity ask), still via Ollama as the execution backend (no llama.cpp FFI work needed; Ollama already handles GGUF+Metal/CPU well). De-dup the existing `index.ts`/`sidecar.ts` near-duplicate copies while touching this. This covers the **desktop/VPS/cloud-hosted tier** of local models.
2. **Promote it from internal-only to a real user-facing `Provider.Info` entry** so downloaded local models flow through the same catalog cloud models already use.
3. **Advertise it as a relay capability** (reuse the existing capability-scoped gating in `agent-daemon`, e.g. add a `models:local` capability) so a paired desktop/VPS runtime that has local models available surfaces that fact to iOS through the *existing* `InstancesClient`/model-catalog path.
4. **Fourth data-plane tier: the iPhone itself.** Add on-device as a genuine data-plane location, following the exact pattern already established for desktop/VPS/hosted (a `Runtime`-trait-shaped abstraction, one contract with multiple location-specific implementations) — not a special case, not a bypass. Concretely:
   - `@allternit/sdk`'s spec (`Allternit_SDK_SPEC.md`) already defines the harness surface as a transport-agnostic typed contract (`Session`, `Message`, `Part`, `AllternitEvent`, `ToolOverrides`) with pluggable transports — today `rpc.ts` (in-process) and `http.ts` (remote). On-device becomes a third implementation of the same contract: a native Swift loop (system prompt assembly → local-model completion via MLX Swift or llama.cpp Swift bindings → parse tool calls → execute against a small native tool registry → repeat), emitting the same `AllternitEvent` shapes the rest of the app already consumes.
   - The loop *pattern* in `session/llm.ts` (system + messages + tool schemas → streamed deltas → tool_calls → execute → continue, via Vercel AI SDK's `streamText`) is a protocol, not Node-specific — that file itself isn't portable (deeply wired to `Config`/`Plugin`/`PermissionNext`/`Auth`), but the shape it implements is exactly what a native Swift loop would reimplement standalone, not port.
   - Tool surface on-device is deliberately small and capability-scoped, not gizzi-code's full tool set — a phone-hosted session has no codebase to run shell/file tools against anyway. Model this after PocketPal's own "Talents" list (calculator, date/time, simple HTML render) plus `sdk.memory.l1`/`l2` read/write for continuity with the rest of the product.
   - Anything needing real tool execution (run code, edit files, browse a repo) is **not** attempted on-device — it escalates through the same cloud control plane every runtime already registers against (see the iOS-pairing note below), to whichever paired desktop/VPS/cloud runtime has the capability, via the SDK spec's already-defined `sdk.sessions.handoff()` primitive. This keeps "intelligent harness" true for on-device sessions without requiring the full harness to exist on the phone.

   **Verified 2026-08-05 — feasibility confirmed, with a corrected mental model on two points:**

   **(a) iOS cannot spawn or run a compiled backend binary, under any circumstances.** This isn't specific to Allternit — iOS has no `fork`/`exec`/subprocess API at all, and App Store Review Guideline 2.5.2 bans executing any code not shipped signed inside the reviewed app bundle. The Electron desktop app's approach (bundle prebuilt `allternit-api`/`gizzi-code` binaries in `resources/bin/`, spawn as subprocesses) has no iOS equivalent — full stop. The only embedding path is compiling Rust to a static library / XCFramework (`aarch64-apple-ios` target) linked into the same signed process via FFI, not spawning anything external. This confirms (doesn't change) the on-device design above: it was never going to spawn `allternit-api` — a from-scratch native Swift loop calling a local model directly is the only workable shape.

   **(b) The VM/Cowork execution engine specifically cannot exist on iOS, which is a feature not a bug for this design.** `allternit-firecracker-driver` needs Linux KVM; `allternit-apple-vf-driver` is `#[cfg(target_os = "macos")]`-gated to Apple's Virtualization.framework — both architecturally excluded from iOS, not just uncompiled for it. This is irrelevant to the on-device *model-hosting* tier, which was already scoped to exclude shell/file/VM execution (no codebase on a phone) — but it does mean "embed the backend on iOS" can never mean the full `allternit-api`, only a thin FFI-embedded shell (model inference + small tool registry, or a local read/offline cache), reinforcing that the on-device tier is its own lightweight implementation, never a port of the desktop binary.

   **(c) iOS pairing precision:** `RuntimePairing.swift` doesn't pair "with the desktop" — it registers the phone as its own independent runtime device type (`ios`) against the cloud control plane, gets its own long-lived device token, the same way desktop/VPS/hosted runtimes each independently authenticate. Desktop gets local VM-driver execution capabilities because it has the drivers; iOS gets relay-only capabilities (`runtime:connect`/`runtime:relay`). There is no iOS-desktop sync problem to solve — each runtime is a client of one cloud source of truth, not a peer needing its own conflict resolution. This is the mechanism `sdk.sessions.handoff()` above rides on.

   **(d) Session-pipeline coupling, verified against the real code (`src/runtime/session/processor.ts`, `prompt.ts`, `compaction.ts`, `tools/guard/permission/next.ts`, `verify.ts`/`loop/verifier.ts`, `hooks/dispatcher.ts`):**
   - **Load-bearing for any loop, including a minimal on-device one:** the core turn state machine (stream deltas → parts → finish-reason → continue/stop), and a hard-coded doom-loop guard (`processor.ts:221-267`) that unconditionally asks for permission if the same tool+input repeats 3 times — a from-scratch Swift loop needs *some* resolution path for this (even a trivial always-allow-once-then-abort), or a hung loop is possible.
   - **Genuinely skippable for a scoped on-device session, confirmed by reading the code, not assumed:** compaction (`compaction.ts:36-52`) only fires on token-overflow and nothing downstream asserts it ran; verification (`verify.ts`) is an opt-in tool call the model must choose to make, never auto-invoked, and its `empirical` mode needs a real dev environment anyway (meaningless without a codebase); hooks (`hooks/dispatcher.ts:23-54`) are a true no-op with no project config, and a phone session has no project directory to load config from in the first place; the SQL-backed permission/session persistence (`session.sql.ts`, local SQLite) only matters for cross-device session visibility, and the existing HTTP session API (`server/routes/session.ts`) is the integration point if that's ever wanted — no new sync plumbing required.
   - **Net verdict:** a from-scratch native Swift on-device loop is feasible as scoped (small tool set, no compaction/verification/hooks needed, one guard condition to satisfy) — nothing found that blocks it or changes the design above.

## Open Decisions for Eoj

- **Finding #3 (hosted-runtime/allternit-api asymmetry) — recommend: intentional, document it, don't add the binary.** Everything `allternit-api` has that `gizzi-code serve` + `agent-daemon` don't (Firecracker/Apple-VF VM drivers, SSH, PTY mux support, the things the desktop launcher embeds) is exactly what the hosted-runtime container doesn't need — its job is harness + relay, which gizzi-code already serves standalone under its mirrored `/v1/*` routes. VM/Cowork execution on cloud-hosted compute is a separate concern from model routing; don't build toward shipping both into that container. Needs your sign-off to close.
- ~~Finding #5 (canonical discovery)~~ — **fully resolved, see the corrected finding #5 above.** Keep both relay/pairing and mesh/tunnel; they're complementary, not competing. One small cleanup surfaced: an untracked, uncommitted `RuntimePairing.swift` draft file duplicates `RuntimeDevicesClient`'s real job under a different name — worth removing or reconciling, not done here since it's not this audit's file to delete unilaterally.
- **Sequencing — recommend: fix tangled edges first, not just because it's lower-risk.** Two concrete dependencies make this an ordering issue, not just hygiene: wiring Sidecar's `ALLTERNIT_SIDECAR_URL`/`_DISABLED` env vars into the hosted-runtime entrypoint (finding #4) is a prerequisite for sanely testing "arbitrary GGUF via HF search" on a cloud box that would otherwise also be auto-pulling a hardcoded model by default; and cloud-hosted terminal/PTY (finding #1) is a live dead feature today, not a hypothetical gap. Still your call, but this isn't a coin flip.
- ~~Finding #7 (Sidecar vs. `@allternit/gizzi-sdk` Local Mode)~~ — **partially wrong, corrected 2026-08-05.** The original resolution ("keep both, gizzi-sdk's harness Local Mode is shared across surfaces including the browser") doesn't hold up: checked directly before building anything against it, and `@allternit/gizzi-sdk` has **zero real consumers anywhere in the monorepo**. gizzi-code's own source only references the name `@allternit/gizzi-sdk` in `config.ts`'s plugin-dependency cleanup, treating it as **deprecated** (superseded by `@allternit/plugin`) — not importing it for anything functional. `cmd/cli` and `ai.allternit.com` both have zero references at all; the "also runs in a browser-hosted mini-app context" claim was wrong.
