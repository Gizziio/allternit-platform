# Allternit Web Surface Schema Deep Dive — Mapping to bb's Thread/Project/Settings/Plugin-Panel UI

## 0. Executive Summary

This report inventories the **web surface** data model under `surfaces/ai.allternit.com/` and maps it to bb's conceptual UI surface: **Threads**, **Projects**, **Settings**, and a **Plugin panel**.

Key findings:

- The web surface has **two declared schemas** that are mostly uncoordinated:
  - **Drizzle SQLite** (`src/lib/db/schema-sqlite.ts`, PG port in `src/lib/db/schema.ts`) — intended local-first/dev schema.
  - **Prisma** (`prisma/schema.prisma`) — legacy/PostgreSQL ORM schema that mirrors much of the Rust API (`cmd/allternit-api`) but is **not imported by the views analyzed**.
- The **running UI** does not use either schema as its source of truth. Threads, projects, tasks, code workspaces, and design projects are stored in **Zustand + `localStorage`** and synced to the Rust API via `src/lib/agents/native-agent-api`.
- bb's first-class entities map to Allternit pieces, but they are **fragmented across local stores, the Rust API, and unused schema tables**. There is no unified bb-style entity graph inside the web DB.

Concrete file paths are cited throughout.

## 1. Web Platform Schema Tables and Their Purposes

### 1.1 Drizzle SQLite / PG schema (`src/lib/db/schema-sqlite.ts`, `src/lib/db/schema.ts`)

These tables are defined in TypeScript and generated by `drizzle-kit`. The SQLite version is the one referenced by `package.json` scripts (`db:generate`, `db:migrate`, `db:push`).

| Group | Table | Purpose |
|-------|-------|---------|
| **Auth** | `user` | Better Auth user identity (`id`, `name`, `email`, `emailVerified`, `image`). |
| | `session` | Better Auth session tokens. |
| | `account` | OAuth/account link records. |
| | `verification` | Email/OTP verification state. |
| **Usage** | `UserCredit` | Per-user credit balance (default 50 credits). |
| **bb-style Project / Thread** | `Project` | Project header (`name`, `instructions`, `icon`, `iconColor`) owned by a user. |
| | `Chat` | Chat thread header (`title`, `visibility`, `isPinned`, optional `projectId`, `kernelSessionId`). |
| | `Message` | Message row per chat (`role`, `content`, `attachments`, `annotations`, `selectedModel`, `selectedTool`, `lastContext`, `activeStreamId`, `canceledAt`, `kernelRunId`). |
| | `Part` | Normalized message parts (`text_*`, `reasoning_*`, `file_*`, `tool_*`, `data_*`, `providerMetadata`). Supports structured content, tool calls, and file attachments. |
| | `Vote` | Per `(chatId, messageId)` up/down vote. |
| | `Document` | Generated artifacts bound to a message (`kind`: text/code/sheet). |
| **Integrations** | `McpConnector` | MCP server configuration (`name`, `nameId`, `url`, `type`, OAuth fields, `enabled`). |
| | `McpOAuthSession` | OAuth flow state for MCP connectors. |
| | `KernelSession` | Kernel-side session linked to a `Chat` (`config`, `status`). |
| **A2UI / Capsules** | `A2UISession` | Per-user A2UI capsule runtime state bound to a chat/message. |
| | `A2UICapsule` | Registry of installable mini-apps/plugins (`manifest`, `contentAddress`, `content`, `status`, `favorite`). |
| **A://Labs** | `ALABSCourse`, `ALABSArticle`, `ALABSCertification`, `ALABSLesson`, `ALABSEnrollment` | Course catalog, content, certifications, and user progress. |

Notes:

- `src/lib/db/schema.ts` is a PostgreSQL port with the same conceptual tables plus `userModelPreference` and `Suggestion`.
- `src/lib/db/migrations-sqlite/0000_salty_echo.sql` only materializes the core auth/chat/project/MCP/A2UI tables; the A://Labs and `A2UICapsule` tables are defined in TypeScript but **not present in the migration**.
- The Drizzle `Project`/`Chat`/`Message`/`Part` tables are currently **not used by the chat/project UI**.

### 1.2 Prisma schema (`prisma/schema.prisma`)

This schema is configured to generate a client to `src/generated/prisma`. It overlaps heavily with the Rust API's SQLite schema and with the Drizzle tables above, but it is not the active runtime schema for the web views.

| Group | Model | Purpose |
|-------|-------|---------|
| **User / infra** | `User` | Clerk-backed user. |
| | `SshConnection`, `RemoteBackendTarget`, `UserBackendPreference` | Remote backend install targets and execution-mode preferences. |
| | `SshKey` | User SSH keys. |
| **Artifact workflow** | `Artifact`, `ArtifactSection`, `ArtifactRevision` | Document-style artifacts with sections and revision history. |
| **Workflow engine** | `Workflow`, `WorkflowExecution` | DAG-style workflow definitions and run records. |
| **Session / reply** | `AgentSession` | Gizzi/agent runtime session proxy. |
| | `Reply` | Streaming reply state per conversation. |
| | `Conversation`, `ConversationMessage` | Lightweight chat threads with branching (`parentConversationId`, `parentMessageId`). |
| **Workspace / board** | `Workspace`, `WorkspaceMember`, `WorkspaceInvitation` | Team/tenant isolation. |
| | `BoardItem`, `BoardComment` | Kanban-style task board. |
| **Skills / runtime** | `TeamSkill` | Plugin SDK manifest registry. |
| | `AgentRuntime` | Runtime discovery/heartbeat. |
| **Agent platform** | `Agent` | Rich agent profile (`type`, `model`, `provider`, `capabilities`, `systemPrompt`, `tools`, `harness`, `avatar`, `identityKey`). |
| | `MemoryEvent`, `MemoryEntity`, `MemoryEdge`, `MemoryDocument` | Memory graph and document store. |
| | `TestSuite`, `AgentMetric` | Evals and run metrics. |
| | `InboxItem` | Photon/mail/inbox notifications. |
| **Cowork engine** | `CoworkProject`, `CoworkSession`, `CoworkScheduledTask`, `CoworkMemoryEntry`, `CoworkPersona`, `CoworkConnector`, `CoworkSuggestion` | Project context, runs, schedules, memory, personas, connectors, and suggestions. |

The Prisma models are the closest in-app representation of the **Rust API** entities. For bb mapping, the API report `ALLTERNIT_NATIVE_PARITY_HANDOFF.md` recommends treating `cowork_projects` as the bb Project backing store and `beta_sessions` as the bb Thread backing store.

## 3. State Management Patterns

### 3.1 Zustand + localStorage (local-first)

Most bb-relevant state lives in Zustand stores persisted to `localStorage` via `src/lib/zustand-browser-storage`:

- `src/views/chat/ChatStore.ts` — owns `ChatProject[]`, thread-to-project mapping, project files/instructions/connectors.
- `src/views/cowork/useTaskStore.ts` — canonical Cowork tasks and `TaskProject[]`.
- `src/views/cowork/CoworkStore.ts` — backward-compatible mirror delegating to `useTaskStore` and `useCoworkUIStore`.
- `src/views/code/CodeModeStore.ts` — code workspaces (`CodeWorkspaceRecord[]`) and sessions (`CodeSessionRecord[]`).
- `src/views/project/design/design-project.store.ts` — design projects and tabs.
- `src/lib/agents/agent.store.ts` — agent registry and selection.

### 3.2 Mode-specific session stores

`src/lib/agents/mode-session-store.ts` is a factory used to create isolated session stores:

- `src/views/chat/ChatSessionStore.ts`
- `src/views/code/CodeSessionStore.ts`
- `src/views/cowork/CoworkSessionStore.ts`
- `src/views/design/DesignSessionStore.ts`

Each store:
- Persists to `localStorage` under a mode-specific key.
- Creates/updates sessions via the Rust API (`native-agent-api`).
- Supports optimistic updates, streaming (`sendMessageStream`), abort, revert/unrevert, compact, and live sync (`connectSessionSync`).

### 3.3 Unified projection for Projects

`src/views/project/unified/useUnifiedProjects.ts` aggregates four mode stores into a read-only `UnifiedProject[]` with fields like `threadCount`, `taskCount`, `fileCount`, `isFavorite`, `isArchived`. It dispatches CRUD back to the owning mode store.

### 3.4 Settings persistence

- `src/hooks/useSettingsState.ts` — simple `localStorage` wrapper under `allternit.settings.v1.<key>`.
- `src/design/ThemeStore.ts` — theme preference.
- Some account/backend/runtime settings are fetched from `setupApi.getConfig()` and cloud endpoints inside `SettingsView.tsx`.

### 3.5 Plugin / capability state

- `src/plugins/feature.store.ts` + `src/plugins/feature.registry.ts` — in-memory feature-plugin registry with `localStorage` enabled overrides.
- `src/views/plugins/fileSystem.ts` / `useFileSystem` — disk scanner for installed plugin packages.
- `src/views/plugins/PluginManager/types.ts` — marketplace install state, personal sources, and connector connection state.

## 4. Gaps Relative to bb's Thread/Project/Settings/Plugin-Panel UI

| bb concept | Current Allternit web state | Gap |
|------------|----------------------------|-----|
| **Project** | Fragmented across `ChatStore.projects`, `useTaskStore.projects`, `CodeModeStore.workspaces`, `DesignProjectStore.projects`. Drizzle `Project` table exists but is unused. | No single bb Project entity in the web DB. A bb-style project cannot see threads across Chat/Cowork/Code/Design. |
| **Thread** | Stored in mode-specific session stores and synced to Rust API `beta_sessions` / `agent_sessions`. Drizzle `Chat`/`Message`/`Part` tables exist but are unused. | Web DB has no authoritative thread/message store; local and API state can drift. The rich `Part` schema is not exercised. |
| **Project ↔ Thread link** | `ChatStore` keeps `threadIds` on `ChatProject`; mode-session metadata has `projectId`. There is no DB FK. | No durable, queryable project-thread relationship in the web schema. |
| **Project context** | Files, instructions, and connectors are stored in `ChatStore` localStorage only. | Project context is not persisted to the Drizzle/Prisma schemas and is lost across devices/sessions. |
| **Settings** | Most settings are `localStorage` strings; `userModelPreference` exists in PG schema but is not read by `SettingsView`. | Settings are not synced across devices and not queryable server-side. |
| **Plugin panel / installs** | Plugin state is in `localStorage` + filesystem scan; `A2UICapsule` table exists but `CapabilitiesManager` does not use it. | No durable plugin-install registry in the web DB; marketplace payments/ratings are absent. |
| **Schema coherence** | Drizzle, Prisma, and Rust API schemas describe overlapping concepts with different column names and shapes. | Merging bb semantics requires choosing one web schema and one API schema, then mapping between them. |
| **Migrations** | `0000_salty_echo.sql` does not include `A2UICapsule`, A://Labs tables, or `UserCredit` details. | Schema and migration are out of sync; adding bb tables needs a new migration. |
| **Event / message parts** | `Part` table supports structured content, but the UI stores flat `content` strings in mode sessions. | bb-style rich events (tool calls, file parts, reasoning) are not normalized in the web store. |

### 4.1 Settings-specific gaps

`SettingsView.tsx` renders ~30 sections from `settings.config.ts`, but:

- No server-side `UserPreference` table is queried.
- Per-mode settings (code theme, Gizzi CLI prefs, Cowork dispatch) are local-only.
- The plugin/settings integration opens `PluginManager` as an overlay, but plugin state is not reflected in a settings DB row.

### 4.2 Plugin-panel-specific gaps

- `src/views/plugins/CapabilitiesManager.tsx` is a rich UI but relies on `localStorage` and scanned files.
- `A2UICapsule` is the natural DB home for installed mini-apps, yet it is not referenced by the plugin manager.
- There is no table for marketplace purchases, ratings, or entitlements.

## 5. Recommended Places to Add bb-Compatible Views and Data Models

### 5.1 Schema changes (Drizzle SQLite as the web cache)

Use the existing Drizzle tables as the local-first bb cache, and sync to the Rust API `beta_sessions` / `cowork_projects` as the authority.

1. **Unify Project/Thread in Drizzle**
   - File: `src/lib/db/schema-sqlite.ts`
   - Add `bbThreadId` / `apiSessionId` to `Chat` so each `Chat` row can map to a Rust API `beta_session`.
   - Add `mode` enum (`chat`, `cowork`, `code`, `design`, `bb`) to `Project`.
   - Add `projectId` FK to a new `SessionLink` table (or to `Chat`) for cross-mode threads.
   - Use `Message`/`Part` to cache messages locally.

2. **Project context tables**
   - Add `ProjectFile` (or use a normalized `projectId` on `Document`) for project-scoped files.
   - Add `ProjectInstruction` table for instructions.
   - Add `ProjectConnector` linking table for mini-app/connector attachments.

3. **Settings table**
   - Extend `userModelPreference` (PG) / add `UserPreference` (SQLite) with `key`, `value`, `scope`, and `updatedAt`.
   - Migrate `useSettingsState` to read/write this table, falling back to `localStorage` offline.

4. **Plugin install table**
   - Use the existing `A2UICapsule` table as the installed-plugin registry.
   - Add `PluginInstall` / `MarketplaceEntitlement` tables for purchase/rating data.

5. **Migration**
   - File: `src/lib/db/migrations-sqlite/0001_bb_web_entities.sql`
   - Add missing `A2UICapsule`/A://Labs tables and the new bb columns/tables.

### 5.2 Data layer additions

- `src/lib/db/projects.ts` — CRUD for bb Projects using Drizzle.
- `src/lib/db/threads.ts` — CRUD for bb Threads/Chats/Messages/Parts.
- `src/lib/db/settings.ts` — read/write user preferences.
- `src/lib/db/plugins.ts` — read/write `A2UICapsule` and marketplace installs.
- `src/lib/agents/bb-sync.ts` — sync local Drizzle cache to/from Rust API `beta_sessions` and `cowork_projects`.

### 5.3 View additions

Create a new `bb` mode under `src/views/project/bb/` and `src/views/chat/bb/`:

- `src/views/project/bb/BBProjectView.tsx` — bb-native project detail using `BaseProjectView`.
- `src/views/project/bb/useBBProjects.ts` — Zustand store backed by `src/lib/db/projects.ts`.
- `src/views/chat/bb/BBThreadView.tsx` — bb-native thread view backed by `Message`/`Part` cache.
- `src/views/settings/bb/BBSettingsPanel.tsx` — settings section backed by `UserPreference` table.
- `src/views/plugins/bb/BBPluginPanel.tsx` — plugin panel backed by `A2UICapsule` and `PluginInstall`.

Wire them into:

- `src/views/project/unified/types.ts` — add `'bb'` to `ProjectMode`.
- `src/views/project/unified/useUnifiedProjects.ts` — include `useBBProjects` in the projection.
- `src/views/project/unified/ProjectDetailRouter.tsx` — route `bb` projects to `BBProjectView`.
- `src/shell/ViewRegistry.tsx` and `src/views/lazyRegistry.ts` — register new view types.
- `src/shell/ShellRail.tsx` — add bb Project / Thread rail entries.

### 5.4 State-management pattern for bb

Follow the existing mode-store pattern:

1. `createBBSessionStore({ name: 'BBSessionStore', storageKey: 'allternit-bb-sessions', originSurface: 'bb' })` in `src/lib/agents/mode-session-store.ts`.
2. Persist project list and settings to Drizzle; persist UI chrome (active project, rail collapse) to `localStorage`.
3. Keep the Rust API (`beta_session_routes.rs`, `cowork_routes.rs`) authoritative for threads/projects, and treat the Drizzle web DB as an offline-first cache.

### 5.5 Migration / rollout order

1. Add `UserPreference`, `PluginInstall`, and bb Project/Thread link columns to `schema-sqlite.ts`.
2. Generate `src/lib/db/migrations-sqlite/0001_bb_web_entities.sql`.
3. Implement `src/lib/db/{projects,threads,settings,plugins}.ts`.
4. Add `bb` mode views and stores without removing existing Chat/Cowork/Code/Design stores.
5. Update `useUnifiedProjects` to include `bb` projects.
6. Optionally backfill existing `ChatStore.projects` into Drizzle `Project` rows.

## 7. Notes & Risks

- **Do not rewrite existing mode stores immediately.** The Chat/Cowork/Code/Design mode isolation is intentional (like Claude Desktop). Add bb as a fifth mode/projection.
- **Schema truth**: The web surface should treat the Rust API as authoritative for threads/projects and use Drizzle SQLite as a local cache.
- **Prisma drift**: `prisma/schema.prisma` contains many useful tables (Cowork, Agent, Memory) but is not wired into the web UI. Consider whether to migrate its models into Drizzle or continue treating them as API-only.
- **Migration sync**: Before adding bb tables, reconcile `schema-sqlite.ts` with `migrations-sqlite/0000_salty_echo.sql` so the baseline migration includes `A2UICapsule` and A://Labs tables.
- **Settings sync**: Moving settings from `localStorage` to a DB table changes the privacy/availability model; use the existing `useSettingsState` fallback when offline.
