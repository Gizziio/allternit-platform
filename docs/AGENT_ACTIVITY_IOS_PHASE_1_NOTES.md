## Base-URL derivation — confirmed against `ACIAgentClient`, not from memory of the map doc

Read `Features/ACI/Services/ACIAgentClient.swift` and `Core/AppConfig.swift` directly before writing anything. `AppConfig.railsBaseURL` is byte-for-byte the same derivation shape as `aciBaseURL` (strip a trailing `v1` path component if present, then `appendingPathComponent("rails")`), added immediately after `aciBaseURL` as instructed. `AgentActivityClient` copies `ACIAgentClient`'s request-building idiom precisely: `init(client: APIClient = .shared, baseURL: URL = AppConfig.railsBaseURL)`, then every call builds via `client.authorizedRequest(url:method:)` + `client.session.data(for:)` + `client.validate(response, data:)` — **not** `APIClient.get/post(path:)`, which is relative to `apiBaseURL` and would resolve to the wrong host entirely, and **not** `client.send(request)` either (that's the relay-aware path `APIClient.get/post` use internally). `ACIAgentClient` itself bypasses `send`/relay routing by calling `client.session.data(for:)` directly — I copied that exactly rather than "fixing" it, since the task said to copy the precedent precisely and relay behavior for rails endpoints is outside this task's scope.

One correction worth flagging: the map doc cited `main.rs:330-331` for the rails mount; the real lines (verified by grep) are `334-335`. Also `main.rs` mounts rails at *both* `/rails` and `/api/rails` (line 334 and 335) — iOS only ever needs the `/api/rails` one, matching the `/api`-prefixed pattern every other AppConfig base URL already follows.

## Entry point: `ComposerPlusSheet`, mirroring `coworkTasksRow`

Chose the `ComposerPlusSheet` menu-row + `.sheet` placement (option (a) from item 6), not a badge/persistent icon (option (b)). Checked for an existing persistent-badge or unread-count convention before deciding — grepped the whole codebase for `badge`/`Badge` usage: every hit is either a local per-row status pill (`AutomationTasksListView.statusBadge`, `CoworkTasksListView.statusBadge`) or an unrelated SF Symbol name (`doc.badge.plus`), never an app-chrome notification-count affordance. There's no tab bar, no persistent top rail, and no equivalent of the web phase's bell icon anywhere in this app's shell. Building one from scratch to hang a badge off of would be inventing a new top-level surface, which the map doc explicitly said to avoid unless a real precedent already existed.

`CoworkTasksListView` is the closest and most current precedent for exactly this situation — "cross-cutting content with no dedicated screen" — solved the same way, same session: a `menuRow` Button (not a `Menu`, since it presents a sheet rather than inline options) plus a `.sheet(isPresented:)` that launches its own internally-`NavigationStack`ed list/detail pair. `agentActivityRow` in `ComposerPlusSheet.swift` copies that shape exactly, placed directly after `coworkTasksRow`.

## What the ledger-tail heuristic actually turned up

Per the constraint to say so plainly if this doesn't turn up anything richer than what web already found: **it doesn't.** The heuristic here is the identical substring match on `event_type` (`/guard/i`, `/reserve/i`, `/review/i`, `/decide/i`) over the same kind of untyped `payload` JSON, filtered by `payload.thread_id`/`payload.mail_thread_id`, windowed to the last 4 relevant events per thread — copied from `AGENT_ACTIVITY_WEB_PHASE_1_NOTES.md`'s own derivation, not reinvented. Confirmed independently while reading `rails/mod.rs`'s `tail_ledger` handler: `payload` is serialized straight from `serde_json::Value` with no documented schema, so iOS has exactly the same "no structured reservation object, no allow/deny signal on guard events" limitation the web phase already wrote up. `AgentActivityDetailView`'s guard/reservation cards render raw `event_type` + relative time only — no fabricated "N paths reserved, 9m left" copy, matching the mockup's *intent* (visibility) without the mockup's assumed data shape (which doesn't exist server-side).

## Assumptions made where the spec was ambiguous

- **"Unread"** is local-only and in-memory (`AgentActivityStore.viewedThreadIds`), not persisted and not backed by a real ack call — there's no `POST /mail/ack` (or equivalent) among the confirmed rails routes for this phase, unlike the web phase's real per-message ack. A thread is marked viewed when its detail view's `.task` fires, mirroring the web phase's "opening the thread is the read signal" reasoning without inventing a network call this backend contract doesn't expose here.
- **Review card copy** stays generic ("a review request with no matching decision yet") rather than echoing the mockup's rich `question`/`recommended`/`alternative` fields, because those don't exist in the real ledger payload — only `event_type` strings do. Showing invented question/recommendation text would violate the "don't invent richer behavior than the real data supports" constraint.
- **`share()` implemented but unwired**: item 2 specifies the client method exactly (`POST rails/mail/share`, body `{thread, asset_ref, note?}`), so it exists on `AgentActivityClient`. Item 5's detail view spec doesn't list a Share action, so nothing calls it — adding a Share button wasn't asked for and would be scope creep beyond the review/reply UI the spec actually describes.
- **Status dot / 5-state mockup treatment was not ported.** The mockup's `review`/`working`/`done`/`idle`/`blocked` status dots assume a per-thread status field that doesn't exist in `AgentActivityThreadSummary` (`{thread_id, messages, last_ts}` — no status). Rather than fabricate a "working"/"done"/"idle" distinction iOS has no signal for, the list view renders capsule tags only for what the ledger heuristic can actually support: Needs review, Guard activity, Reservation — the same simplification-to-real-states judgment call the web phase made (three real states instead of the mockup's five), applied here to tags instead of a status dot since iOS has even less signal (no archive call in scope, so no active/archived distinction either).
