## 0. What we're building

The target shape is a "universal context layer": connect to 10+ personal/professional
data sources (Gmail, Notion, Calendar, GitHub, Linear, Slack, LinkedIn, Drive,
Obsidian, HubSpot), continuously extract and structure that data into tagged,
permissioned profiles, and serve it to any AI tool (Claude, ChatGPT, Cursor) over
MCP — connect a source in under a minute, no manual re-explaining context to
every tool ever again.

We are not starting from zero. Allternit already has four of the five pieces
this needs, just not wired together:

| Layer | Allternit piece | Location |
|---|---|---|
| MCP distribution | Working MCP protocol impl | `mcp/core`, `mcp/mcp-client`, `mcp/servers` |
| Permissions | Capsule-scoped permission checks | `mcp/servers/src/permissions.ts` |
| Structuring/profile | Markdown+graph memory store, typed entities, query API | `cmd/gizzi-code/src/vault/` |
| Continuous sync | Real cron scheduler already driving 3-source sync | `cmd/gizzi-code/src/runtime/automation/cron/executors/vault-sync-executor.ts` |
| Connectors (the gap) | 3 competing, mostly-stubbed systems (see gap-analysis doc) | `mcp/connectors`, `domains/cowork/connectors`, `cmd/allternit-api/src/connector_routes.rs` |

## 1. Connector backbone decision — open-connector, not System C

`docs/gap-analysis/OPEN_CONNECTOR_GAP_ANALYSIS.md` (2026-07-11) recommended
consolidating the three in-house connector systems onto System C (the Rust
catalog+dispatcher). **This plan deliberately does not follow that
recommendation for the context-layer product.** Reasoning:

- System C only has 3 of 181 catalog entries actually wired end-to-end. Getting
  it to 10+ working sources means writing OAuth + dispatch metadata
  for 7+ providers from scratch in Rust.
- The vendored `services/open-connector` (oomol-lab, Apache-2.0, already sitting
  in the tree at `allternit/services/open-connector`) has 1,000+ providers that
  actually execute, automatic OAuth2 refresh, AES-256-GCM credential storage,
  and — critically — **already exposes its own MCP endpoint** (`POST /mcp` with
  `list_apps`/`search_actions`/`execute_action`). It is closer to the target
  collection layer today than anything we'd build in System C in the same
  timeframe.
- System C remains the right engine for *in-product, agent-invoked tool actions*
  (Design surface, Plugin Manager) — that's a different use case (an agent
  deliberately calling a tool mid-task) from this product (passive background
  context ingestion). The two don't need to converge. This plan does not touch
  System A, B, or C — they're left exactly as the gap-analysis doc describes.

Open decision to flag, not resolved here: `open-connector`'s encryption key is
explicit-opt-in via `OOMOL_CONNECT_ENCRYPTION_KEY` (warns if unset), whereas
System C auto-provisions from the OS keychain. Phase 1 should mirror System C's
keychain default rather than shipping with open-connector's weaker default.

## 2. Phased build

### Phase 1 — Stand up the connector engine
- Fork a working copy of `services/open-connector` into its own service
  directory (don't build directly on top of the vendored reference copy —
  keep that as the upstream-diff baseline so future `git pull`-style upgrades
  stay clean).
- Run it locally (Docker or Node — not Cloudflare Workers; keep secrets local,
  consistent with how `allternit-ops` was scoped to local-only Stripe/Cloudflare
  keys).
- Wire `OOMOL_CONNECT_ENCRYPTION_KEY` to auto-provision from the OS keychain the
  same way System C's `token_crypto.rs` does, instead of a raw env var.
- Pick and configure the MVP provider set — recommend a reduced scope:
  **Gmail, Google Calendar, Notion, GitHub,
  Linear, Slack** (6 sources — enough to prove the "connect once, every tool
  sees it" story without a long OAuth-app-approval slog).
- Verify each provider via its own `execute_action` and REST calls before
  moving on.

### Phase 2 — Structuring pipeline (extend Vault, don't replace it)
- Extend `Vault.Frontmatter` (`cmd/gizzi-code/src/vault/types.ts`) with a
  `sensitivity: "public" | "private" | "restricted"` field — `tags`, `entities`,
  and `source` already exist and cover most of the tagging requirement.
- Decide how "profile" is represented: either a new synthesized index note per
  connected identity (role, projects, focus areas, tech stack, generated by a
  summarization pass over recent Notes) living under a `profile/` folder, or a
  computed view over existing entities rather than a new `EntityType`. Needs a
  call before Phase 2 starts — not decided in this doc.
- Write one generic `extraction-pipeline.ts`: takes an open-connector
  `execute_action` result for a given provider → maps to a Vault `Note` with
  `entityType`/`tags`/`source`/`sensitivity` populated → writes via
  `vault/io.ts`. This replaces the pattern of one hand-written file per source
  (`sync/gmail.ts`, `sync/calendar.ts`, `sync/fireflies.ts`) with one
  metadata-driven mapper, matching open-connector's own
  "definition, not code, per provider" philosophy.

### Phase 3 — Generalize continuous sync
- Refactor `vault-sync-executor.ts` from its current hardcoded 3-source switch
  into a loop over a source registry keyed by open-connector provider ID, each
  entry pointing at the Phase 2 generic extractor.
- Extend `VaultUserSettings.sources` (`vault/settings.ts`) from the current
  `{gmail, calendar, fireflies}` fixed shape to a map keyed by provider ID, so
  enabling a new source doesn't require a code change.
- `SyncConfig.intervalMinutes` / `lookbackDays` already exist — reuse as-is.

### Phase 4 — MCP context-serving endpoint (the actual product surface)
- New MCP server (TypeScript, `@modelcontextprotocol/sdk` — already a
  dependency in `cmd/gizzi-code/package.json`) exposing context-query tools
  (e.g. `search_context`, `get_profile`, `get_recent_activity`) backed by
  `vault/search.ts`.
- This is a distinct endpoint from open-connector's own `/mcp` (which exposes
  *action execution*, not context querying) — don't conflate the two; an AI
  tool connects to *this* server to read context, not to trigger Gmail sends.
- Enforce sensitivity/source filtering here using `mcp/servers/src/permissions.ts`'s
  capsule model, extended from its current coarse on/off scoping to per-source
  filtering on query results — this is the specific permission-granularity gap
  the earlier gap-analysis doc flagged, now scoped narrowly to context reads.
- Register the server the same way `allternit-ops` was registered for the
  business-ops MCP work — document the opt-in step, don't auto-register.

### Phase 5 — Onboarding surface
- Open decision, not resolved here: CLI flow inside `gizzi-code` (fastest,
  matches existing patterns) vs. a page on `ai.allternit.com` (more
  polished onboarding UX). Pick before starting Phase 5.
- Whichever surface: trigger open-connector's OAuth flow → flip the matching
  `sources[providerId].enabled = true` in vault-settings → fire one immediate
  sync instead of waiting for the next cron tick, so the "90 seconds to
  AI-ready context" claim is actually true on first connect.

### Phase 6 — Hardening (lower priority, do after MVP proves out)
- Confirm open-connector's automatic OAuth refresh is actually exercised for
  all 6 MVP providers, not just assumed from its docs.
- Surface execution-status honesty (`locallyExecutable`/`needsCredential`) in
  whatever Phase 5 UI exists, mirroring the gap-analysis doc's "catalog honesty"
  recommendation.
- Two-way sync (AI tool actions writing back into source systems) — explicitly
  **out of scope for MVP**. It's a materially bigger
  trust/safety surface (an agent silently modifying Gmail/Notion on your
  behalf) and deserves its own review gate, not a default-on feature bundled
  into the context layer.

## 3. Explicitly out of scope / deferred
- Systems A/B/C consolidation — untouched, tracked separately in the
  gap-analysis doc.
- LinkedIn, Drive, Obsidian, HubSpot connectors — not in MVP provider set,
  add after the 6-source MVP proves the pipeline end-to-end.
- Hosted/multi-tenant deployment — this is being built for internal/Allternit
  use first, not as a shipped product to external customers, until proven out.
- Two-way sync (see Phase 6).

## 5. Phase 0 decisions (made 2026-08-04, build proceeding)

1. **Name: "Allternit Lens".** Distinct from `allternit-brain` (business-ops
   knowledge base, separate repo under `Allternit/`) and from `Vault` (the
   underlying storage this builds on) — Lens is the thing that gives outside
   AI tools a view into Vault's contents. Service directory: `services/lens-connector`
   (forked from `services/open-connector`), MCP server:
   `mcp/servers/lens-context-server` (Phase 4).
2. **Profile representation: synthesized, regenerated note.** Each sync cycle
   regenerates a note under `profile/<providerId-or-identity>.md` by
   summarizing recent Notes for that source (role, active projects, focus
   areas, tech stack style fields in frontmatter) rather than introducing a
   new `Vault.EntityType`. Reasoning: keeps the entity-type enum stable (no
   downstream code that pattern-matches `EntityType` needs updating), gives
   the MCP `get_profile` tool a single fast file read instead of a live
   aggregation query, and matches Vault's existing "notes are the interface"
   design.
3. **Onboarding surface: CLI.** Ships inside `gizzi-code` rather than as a new
   `ai.allternit.com` page — reuses existing CLI command patterns, avoids a
   second OAuth-callback web surface, and doesn't block on a web app-review
   cycle with any provider. Revisit web onboarding post-MVP if Lens becomes
   something non-technical users need to self-serve.

**What changed:**
- Vault's storage root now resolves via the same `resolveBrainPath()` logic
  `gizzi brain` uses (`--path` flag → `userSettings.brain.path` →
  `~/brain`), extracted from `cli/commands/brain/status.ts` into a neutral
  `src/runtime/brain/path.ts` both sides import — `vault/index.ts`'s
  constructor is the single choke point, so all 13 existing call sites
  (CLI, HTTP routes, tool builtins, cron, MCP server) picked it up with no
  other changes needed.
- `VaultManager.initialize()` now bootstraps a brand-new root with
  `initBrain()` (git init + identity.md/MEMORY.md/domains/decisions/
  runbooks/ideas templates) *before* creating Vault's own structural
  folders — so `gizzi vault sync` and `gizzi brain init` agree on one
  bootstrap regardless of which a user runs first.
- `Vault.EntityType` gained `identity | domain | runbook | idea` (brain's
  template types). Entity-type inference (`vault/index.ts` query filter,
  `vault/graph/build.ts`) now prefers `frontmatter.type` over folder-name
  guessing — required because `identity.md`/`MEMORY.md` live at brain root
  with no folder to infer from, and replaces an unchecked `as EntityType`
  cast in the graph builder with a validated one.
- `.gitignore` (covering `Topics/`, `profile/`, `.allternit/` — Lens's
  auto-synced content and Vault's own SQLite index, never the user's
  authored notes) is now part of the brain init template, plus an
  idempotent top-up in `ensureVaultStructure()` for brains initialized
  before this change.
- Explicitly untouched, by design: the "legacy" SQLite triple-store
  (`runtime/brain/brain.service.ts`, self-labeled legacy, confirmed not
  wired into anything but the `gizzi brain memory` CLI), the
  `vault-settings.json`/`userSettings.brain.path` split (different
  concern — per-source config vs. storage root), and no mechanical
  `Vault`→`Brain` rename across HTTP routes/types/GUI (Vault = the engine,
  Brain = the location it now runs on top of).

**One real bug found and fixed during live testing, not caught by review or
typecheck:** the first bootstrap attempt silently skipped `initBrain()`
entirely. Cause: `VaultIndex`'s constructor creates `.allternit/vault-index.db`
*before* `initialize()` ever runs, so by the time the "is this root empty"
check ran, the directory already had a file in it. Fixed by filtering
`.allternit` out of the emptiness check and passing `force: true` into
`initBrain()` (safe — the `.gitignore` template is written before `git add
-A` runs, so `.allternit/` still never lands in the initial commit).
