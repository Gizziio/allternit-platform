# Agent Activity design — v2 audit + v3 redesign

## What Rails Mail's real action surface actually is

Before critiquing the UI, I read the backend it's supposed to represent: `cmd/allternit-api/src/rails/mod.rs` (the HTTP layer) and `rails/src/mail/mail.rs` / `rails/src/service.rs` (the actual implementation). A few things that aren't obvious from the API list in AUDIT_TASK.md but matter a lot for the UI:

- **`decide()` is strictly boolean** (`rails/src/service.rs:988`, `MailDecideRequest { decision: Option<String>, approve: Option<bool>, ... }` — resolves to `"accepted"`/`"rejected"`, nothing else). There is no 3-way or N-way decision in the real API. Any "which of these options" ask an agent poses has to collapse into "approve the recommended option, or don't" before it ever reaches `decide()`. A UI that doesn't make the recommended option explicit is silently asking the human to approve/deny something whose *content* isn't stated anywhere in the API call itself — the content only exists in the free-text message body.
- **`reserve()` and `guard()` have no human-facing verb at all** (`rails/src/service.rs:452` `MailReserveRequest`; `rails/src/mail/mail.rs:188` `guard_action` just logs a `MailGuardAction` event with `action`/`detail`). These are agent/system-only calls — a human never *calls* reserve or guard. But their **effects** (a path lock blocking another agent, a policy denial that stopped an agent mid-task) are exactly the kind of state a human watching this panel needs to see, per this repo's own documented pattern of concurrent agent sessions (`GIZZI.md`: "multiple concurrent Eoj/agent sessions editing the same checkout at once... resolve with a fast-forward merge, not by treating it as your own scope creep").
- **`archive()` and `share()` are real, separate calls**, not aliases for `decide()` or `send()`. v1 exposed them (`Archive` / `Share asset` buttons in the detail header); v2 dropped both entirely — the only actions left in v2 were Approve/Deny (`decide`) and a reply box (`send`).

## Audit findings on `mockup-v2.html`

Each finding includes a concrete scenario, not just a verdict.

### 1. v2 flattens away real, distinct actions — specifically loses `archive()` and `share()`
v1 had `Archive` and `Share asset` buttons in its detail header. v2's rewrite ("rebuilt around real production patterns") dropped them without replacement — the only per-thread actions left are Approve, Deny, and a reply input. **Failure scenario**: a resolved thread (e.g. `wih:executor-cowork-tasks`, merged as PR #13) has no way to leave the "All" list short of it happening to also carry `resolved: true` styling — there's no user-triggered archive at all, and no way to attach a build artifact or screenshot into a thread (`share()`) without falling back to some other, undesigned surface. Over weeks of real use, "All" only grows.

### 2. `reserve()`/`guard()` conflicts are completely invisible
Neither v1 nor v2 show reservation or guard state anywhere. **Failure scenario**: two concurrent executor threads both need to touch `GoalEngine+Client.swift`. One holds the reservation; the other gets denied by `guard()` and stalls. In v1/v2, the stalled thread just... stops updating, with no visible reason. A human watching Agent Activity has no way to tell "this is blocked on a lock held by another thread I can see right above it" from "this agent silently died." Given this repo's documented history of concurrent sessions colliding, this is not a hypothetical.

### 3. Information density / scale: no read state, no archive, no filters beyond two tabs
v2 removed v1's `read`/`unread` tracking entirely — every row looks identical whether it's brand new or already seen. Combined with only two tabs (All / Review) and no bulk actions, no keyboard shortcuts, and no grouping, this doesn't hold up past a handful of threads. **Failure scenario**: this repo's own session generated ~10 executor threads in one sitting per AUDIT_TASK.md's own framing; a heavy user with dozens of threads across days has to scroll a flat, undifferentiated list in a 380px slide-over to find "the one from yesterday," with nothing to mark it seen or shrink the working set. Compare: Linear Triage handles volume with number-key triage (`1`/`2`/`3`/`H`) plus Triage Rules automation; GitHub's notifications inbox handles it with reason-based default filters plus a Done/Save split that actually removes items from the working list. v2 has none of these mechanisms.

### 4. Accordion-only disclosure has no escape hatch for long threads
v2's own banner cites Claude Code's Agent View as the model — "inline preview... Enter for full transcript." But v2 only built the inline half: the accordion's `max-height: 320px; overflow-y: auto` is the only way to read a thread, with no full-transcript view. **Failure scenario**: a real executor thread that runs for hours accumulates 20+ messages; a 320px scroll box inside a 380px-wide panel is a bad way to read that history, and there is no `Enter`/expand affordance to escalate to something roomier, despite v2's own banner claiming to follow the product that has exactly that affordance.

### 5. "View diff" assumes every review request is a GitHub PR — it isn't
`requestReview(threadId, wihId, diffRef)` takes an opaque `diffRef` string — nothing in the API guarantees it's a GitHub PR reference. v2 hardcodes the link as "View diff — PR #N" styling regardless. **Failure scenario A**: an agent asks for review before it's opened a PR (a local diff, or a design question with no code at all) — v2's template just omits the diff-link (`diffRef: null`) and shows Approve/Deny naked, with nothing describing what's being approved. A human could approve blind. **Failure scenario B**: even for real code-diff requests, the confirmed real review surface in this repo is a GitHub PR (`gh pr view`/`gh pr diff` — how this session's own PRs #4, #9, #13 actually got reviewed), but that's true only for *code* review requests. `decide()` is used for any yes/no gate, not just code review — routing every `requestReview` to "open a GitHub PR" is a category error for the non-diff case, and v2 has no second code path.

### 6. Visual/interaction execution
- The pulse animation on `.status-dot.working` doesn't respect `prefers-reduced-motion` (DESIGN.md §6.3 requires this) and status is conveyed by color alone — no text or icon fallback, which also fails DESIGN.md §7.1 contrast/non-color-reliance intent for anyone colorblind.
- The tab bar (All/Review) is the only filtering mechanism — insufficient per finding 3.
- Approve/Deny sit directly below a one-line `preview` string and an unclicked diff-link; a user can act without having actually seen the diff or, in the non-diff case, without any description of the ask at all (ties to finding 5).
- v1's avatar circles (initials, color-coded by role) were dropped in v2's accordion in favor of text-only "who" labels — weaker scannability in exchange for compactness, a reasonable tradeoff for the accordion specifically but worth naming.

### 7. Cross-surface translatability
The underlying IA (a filterable list of threads, each with a status, a preview, and either 0 or 1 pending decision) translates fine to mobile and CLI. What doesn't:
- **Hover states** (`:hover` on rows, buttons, the diff-link) have no equivalent on touch or in a terminal — v2 relies on them as the only affordance for "this is clickable" in a few places.
- **A fixed 380px slide-over** is a web-only idiom; mobile needs a full-screen route (GitHub Mobile's deployment-approval dialog *is* the full screen, reached only via notification — there's no slide-over equivalent on their mobile app), and a CLI needs a plain scrolling list.
- **Mouse-driven accordion expand** with no keyboard path at all — v2 has zero keyboard interaction. A CLI list is inherently keyboard/arrow-driven; retrofitting that after the fact onto a mouse-only design is exactly the kind of gap that turns into "iOS/CLI parity has to be built by hand, badly" that `GIZZI.md` warns about.

## New sources pulled in for this audit

- **Linear Triage** — https://linear.app/docs/triage — number-key triage (Accept `1` / Duplicate `2` / Decline `3` / Snooze `H`), Triage Rules automation and shift-click OR-filters for scale.
- **Linear Triage Intelligence** — https://linear.app/now/how-we-built-triage-intelligence — AI suggestions are always shown with visible reasoning (hover tooltip, a "thinking panel" with the full decision trace) and are opt-in to auto-apply, never silently applied — relevant to any future "AI-suggested triage" on top of Rails Mail threads.
- **PagerDuty incidents** — https://support.pagerduty.com/main/docs/incidents — filterable Timeline tab; Acknowledge / Escalate / Resolve as a persistent action bar, not a one-shot inline button that disappears.
- **PagerDuty mobile app** — https://support.pagerduty.com/main/docs/mobile-app — status-color banner (red → yellow on acknowledge), swipe-left-to-Ack / swipe-to-Resolve on the list, and **long-press a push notification to Ack without opening the app at all** — the closest real analog to a mobile `decide()` flow.
- **GitHub notifications inbox** — https://docs.github.com/en/subscriptions-and-notifications/how-tos/viewing-and-triaging-notifications/managing-notifications-from-your-inbox — reason-based default filters (mention/review-requested/participating), and critically, **Done vs. Save** as the mechanism that actually keeps the inbox from growing forever (Done removes from the working list but keeps for 5 months; Save bookmarks indefinitely).
- **GitHub Mobile push notifications** — https://github.blog/changelog/2021-11-22-push-notifications-for-pull-request-review-activities-on-github-mobile/ and https://github.blog/changelog/2021-04-01-reviewing-deployments-on-github-mobile/ — on mobile, the push notification is the *only* entry point into a deployment-approval dialog; there's no equivalent slide-over.
- **Slack mobile approval-request tutorial** — https://docs.slack.dev/tools/deno-slack-sdk/tutorials/mobile-request/ — a Block Kit message with a primary "Approve" button and a danger-styled "Deny" button; on click, the buttons are replaced in place with the resulting decision (no dead, still-clickable state after a decision is made).

## What changed in v3, and why

- **Restored `archive()`/`share()`** as first-class actions via a per-row `⋯` menu, separate from the `decide()`-driven Approve/Deny — addresses finding 1. Kept them out of the primary row content so they don't compete visually with the fast Approve/Deny path (a lesson from Slack's Block Kit pattern: the primary decision stays primary).
- **Reservation and guard state are now visible.** A thread holding a lock shows a `🔒 N paths · Nm left` tag on the row and a note in the expanded view; a thread blocked by `guard()` gets a distinct status (`blocked`, red dot, "⛔ Blocked by guard" tag) and its guard message renders in a visually distinct warning card, not a plain agent bubble — addresses finding 2. This is deliberately *read-only* — no "release lock" button — because reserve/guard are agent/system actions with no human-facing verb in the real API; the UI's job here is visibility, not control.
- **Unread state and a real Archived tab are back**, restoring what v1 had and v2 dropped, plus the badge count on the bell now reflects actual unread threads — addresses finding 3. (v3 doesn't attempt Linear's full Triage Rules automation or GitHub's 15-custom-filter system — that's real scope for a later pass once the core IA is approved, noted under `remaining`.)
- **Accordion still previews the last two messages inline** (cheap, matches Claude Code's inline-preview habit) but now has an explicit **"Open full thread →"** escalation into a dedicated detail view with a back button, showing the complete message history — addresses finding 4, and is also the piece most directly reusable across surfaces: on mobile this becomes a full-screen push; on a CLI it's exactly "select a row, press Enter."
- **Review cards are now typed by kind**, not templated as a bare diff link. `kind: "code-diff"` shows the PR ref plus a stat line (`+216 −12 · 3 files`) so a diff-size sense exists even without clicking through. `kind: "decision"` (a `decide()` call with no diff at all) shows the actual question and the agent's recommended option inline, worded to match `decide()`'s real boolean semantics ("Approve recommendation" / "Reject") instead of pretending it's a 3-way choice — addresses finding 5's blind-approve problem and the API's real constraint noted above.
- **Keyboard interaction throughout**: `↑↓`/`j k` to move focus, `Enter` to open the full thread, `1`/`2` to approve/deny, `a` to archive, `Esc` to back out — modeled directly on Linear Triage's number-key pattern. This is the single change that does the most for finding 7 (cross-surface translatability), since it's the one interaction model that maps cleanly onto a terminal list without modification.
- **Accessibility**: the pulse animation is now wrapped in `@media (prefers-reduced-motion: no-preference)`; every status dot has a screen-reader-only text label (`sr-only` span) alongside the color, so status is never conveyed by color alone; focus rings use `outline: 2px solid var(--accent-primary)` per `DESIGN.md` §7.2.
- Kept from v2, unchanged, because the audit didn't find a problem with them: the header-icon → slide-over entry point (vs. a dedicated page — still matches GitHub's Copilot Agents panel and doesn't compete with primary nav), and the general instinct to route code-diff review requests toward the real GitHub PR surface rather than reinventing diff rendering.
