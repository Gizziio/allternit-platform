After that, `gizzi mail --help` and every subcommand ran.

## A real hang, found live and fixed

Running `gizzi mail decide mail:cli-phase1-test` with neither `--approve` nor `--reject` printed `❌ one of --approve or --reject is required`... and then never returned. `ps` showed the `bun` process still alive minutes later; I had to `kill -9` it. This is exactly the "process-exit gotcha" the map doc told me to watch for, but in a form I hadn't anticipated from reading `status.ts`'s precedent alone: my validation lived in a yargs `.check()` callback, which throws *before* my command handler (and its `process.exit` calls) ever runs. Yargs' own error path catches the throw, this app's global handler prints `Unexpected error, check log file at ~/.local/share/gizzi-code/log/dev.log for more details` — and then the process just sits there, because nothing in that path calls `process.exit()`. (`.conflicts('approve', 'reject')` — the `--approve --reject` case — turned out fine, exiting immediately with code 1; the hang was specific to the thrown `.check()` error.)

Fix: moved both the "exactly one of approve/reject" check and the mutual-exclusivity check into the handler's own `try`/`catch`, so `process.exit(1)` is always reachable regardless of which validation fails. Reverified live against the same running instance — all four `decide` invocations (missing flag, both flags, `--approve`, `--reject`) now exit promptly with the right code and message.
