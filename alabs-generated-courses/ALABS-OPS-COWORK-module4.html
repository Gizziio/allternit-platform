Module 4: Scaling Cowork Across a Team

Cowork is powerful for one person, but it becomes a platform when an entire team shares workspaces, personas, and governance. This module shows how Allternit uses RBAC, workspace isolation, permission profiles, and approval gates to roll out Cowork safely.

5 lessons · ~40 minutes Source: packages/@allternit/cowork-engine

RBAC and workspace isolation

Allternit's security model scopes every resource — agents, sessions, files, memory — to an organization and, where applicable, to an individual user. Organization owners and admins manage workspaces, keys, budgets, DLP rules, and analytics. Members operate inside the workspaces they are assigned.

Cowork workspaces follow the same boundary. A workspace is not just a folder; it is a container for shared memory, personas, projects, and audit context. Creating a workspace is an admin action recorded in the audit feed under workspace.create.

RoleCan manage workspacesCan manage keys/budgetsCan approve high-risk actions
OwnerYesYesYes
AdminYesYesYes
MemberNoNoOnly if explicitly assigned

Isolation principle: every Cowork memory entry is keyed by userId and can be narrowed with projectId or sessionId. Shared workspace context lives at the project or workspace level; personal preferences stay at the user level.

Permission profiles as presets

The gizzi-code CLI ships with named permission profiles that bundle sandbox boundaries, network access, tool approvals, and writable roots. Profiles let a team move quickly between restrictive and permissive modes without editing config.toml by hand.

ProfileSandboxNetworkBest for
restrictedblockedoffUntrusted code or sensitive repos
workspace-writeworkspace onlyoff by defaultDay-to-day engineering tasks
trusted-reviewworkspaceapproval requiredCode review in known repositories
danger-full-accessdisabledonOnly when the environment already isolates processes

Custom profiles live in ~/.gizzi/profiles/<name>.toml. The CLI loads configuration in this order: user defaults → named profile → project overrides → CLI flags. Because the profile is a layer above your base config, it only needs to contain the values that differ.

toml
# ~/.gizzi/profiles/team-review.toml
[permissions]
approval_policy = "on-request"
sandbox_mode = "workspace-write"
network_access = true
allow_login_shell = false

[permissions.sandbox_workspace_write]
writable_roots = ["/path/to/workspace"]

[permissions.tools]
allow_bash = true
allow_filesystem_write = false
allow_subagents = "on-request"

Governance with approval gates

Even with the right profile, some actions are too risky to run unattended. The Cowork engine's ApprovalGate class turns risky actions into explicit requests.

Each pending approval carries a riskLevel of low, medium, high, or critical, plus a summary, action type, target, arguments, and consequence. Auto-rules can approve low-risk actions instantly; everything else waits for a human.

typescript
const gate = new ApprovalGate({
  defaultTimeoutMs: 120_000,
  autoRules: ApprovalGate.buildDefaultRules(),
  onRequest: (approval) => ui.showApprovalCard(approval),
  onResult: (result) => audit.recordDecision(result),
});

const result = await gate.request({
  actionId: 'write-package-json',
  sessionId: session.id,
  riskLevel: 'high',
  summary: 'Modify package manifest',
  details: {
    actionType: 'filesystem.write',
    target: 'package.json',
    args: { content: '...' },
    consequence: 'Changes project dependencies',
  },
});

Team rollout flow

A safe rollout follows four phases: provision, profile, pilot, and monitor. The diagram below shows how admin actions, permission decisions, and audit logging fit together. 

flowchart LR
    A[Org Admin] --> B[Create Workspace]
    B --> C[Assign Members]
    C --> D[Permission Profile]
    D --> E{Approval Gate}
    E -->|low risk| F[Auto-approve]
    E -->|medium+| G[Human Review]
    F --> H[Execute Action]
    G --> I[Approve / Reject / Timeout]
    I --> H
    H --> J[Audit Log]
    J --> K[Compliance Export]

Phase 1 — Provision

Admins create workspaces that match team boundaries. Use the allternit admin workspaces command group or the admin API. Every create/update/delete call is recorded in the audit feed.

Phase 2 — Profile

Choose or define permission profiles for each workspace's risk level. Start restrictive and relax only after the team demonstrates good review habits. Avoid danger-full-access unless the host environment already isolates processes.

Phase 3 — Pilot

Run a small group through real tasks. Watch approval gate metrics: timeout rate, rejection rate, and average time-to-decision. High timeout rates usually mean the approval UI is interrupting flow too often; tighten auto-rules or split tasks into smaller steps.

Phase 4 — Monitor

Use audit logs and usage events to review who created workspaces, changed roles, and approved risky actions. Compliance endpoints can export or delete workspace data when required.

Capstone: Design a team Cowork policy

Choose one team in your organization and design a Cowork rollout plan. Define the workspace boundaries, pick permission profiles for different roles, list three actions that must go through the approval gate, and describe how you will review audit logs weekly.

Workspace

Name, slug, and member roles for the pilot workspace.

Profiles

Which built-in or custom profile applies to each role.

Approval gate rules

Three action types or risk levels that require human review.

Audit review

Queries and cadence for checking workspace and approval events.
