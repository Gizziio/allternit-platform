Agent graphs: routing, chaining, and parallelization

A single model call is rarely enough for production tasks. Useful agents decompose work into smaller steps and decide what to do next. The three fundamental graph patterns are:

  • Routing. A classifier node inspects input and dispatches to a specialist branch. The support triage playbook classifies a ticket as Billing, Technical, Account, or Feature Request, then routes accordingly.
  • Chaining. Output from one node feeds directly into the next. A research agent may search, summarize, cite, and then format a final answer as a sequence of dependent nodes.
  • Parallelization. Independent branches run at the same time and their results merge. A code-review agent can run style, security, and correctness checks in parallel before aggregating findings.

Graphs are state machines. Every node reads from an execution context, produces a result, and triggers downstream nodes only when its dependencies are satisfied.

The Allternit Workflow Engine

packages/@allternit/workflow-engine/src/engine/workflow-engine.ts implements a DAG-based execution engine. A workflow is a list of nodes and connections; an execution is a stateful run of that workflow with its own context.

Core concepts

  • Workflow — a declarative graph: nodes, connections, inputs/outputs schema, and triggers.
  • WorkflowNode — an instance of a node type with configuration and mappings.
  • Connection — a directed edge from a source node to a target node, optionally guarded by a condition.
  • ExecutionState — live state: active nodes, completed nodes, failed nodes, and node results.
typescript 
import { createWorkflowEngine } from '@allternit/workflow-engine';

const engine = createWorkflowEngine();

engine.registerWorkflow({
  id: 'research-and-summarize',
  name: 'Research and summarize',
  version: '1.0.0',
  nodes: [
    { id: 'trigger', type: 'trigger:manual', name: 'Start' },
    { id: 'search', type: 'http:request', name: 'Search',
      config: { method: 'GET' } },
    { id: 'summarize', type: 'transform:map', name: 'Summarize',
      config: { expression: 'data.results.map((r) => r.snippet).join(String.fromCharCode(10))' } },
    { id: 'output', type: 'output:result', name: 'Result' },
  ],
  connections: [
    { id: 'c1', source: 'trigger', target: 'search' },
    { id: 'c2', source: 'search', target: 'summarize' },
    { id: 'c3', source: 'summarize', target: 'output' },
  ],
});

const run = await engine.execute('research-and-summarize', { query: 'Allternit harness' });
console.log(run.status, run.outputs);

The orchestrator layer

While the workflow engine runs deterministic graphs in-process, the orchestrator package (packages/@allternit/orchestrator) manages long-lived agent sessions across backends: local terminal, multiplexer, kernel, cloud, and delegated executors.

Session lifecycle

  • A SessionSpec defines the agent vendor, launch command, working directory, isolation strategy, task file, and completion sentinel.
  • An ExecutorBackend spawns the session, sends prompts, tails output, watches for completion, and kills the session.
  • SessionRegistry tracks active sessions and emits session.spawned, session.prompted, session.done, and related events.
  • The completion contract is a YAML-frontmatter notes file; its existence is the only completion signal.
typescript 
import { LocalTerminalBackend } from '@allternit/orchestrator';

const backend = new LocalTerminalBackend();

const session = await backend.spawn({
  slug: 'refactor-payment-service',
  workdir: '/workspace',
  vendor: 'kimi',
  mode: 'headless',
  launchCommand: 'gizzi --mode headless',
  notesFile: '.allternit/notes.yaml',
  timeoutMs: 600_000,
});

await backend.send(session, 'Refactor the payment service to use the new harness.');
const outcome = await backend.watch(session, session.spec);
console.log(outcome.kind); // 'done' | 'dead' | 'timeout'

Verified send. The orchestrator pastes a prompt, reads it back, and submits only when the pasted text matches, preventing partial or corrupted instructions.

Advanced agent store

The platform surface in surfaces/ai.allternit.com/src/lib/agents/agent-advanced.store.ts exposes graph concepts through a Zustand store: subagents, swarms, workflows, templates, and advanced configuration. These map to the orchestrator and workflow engine underneath.

Subagents

A parent agent can spawn subagents with scoped configs. The store fetches, creates, updates, and deletes subagents under a parent agent id and exposes a spawnSubagent action that returns a run id.

Swarms

Swarms are multi-agent runs. The store supports creating a swarm, joining agents with roles, starting a run, and exchanging messages. Swarm events update the store reactively.

Workflows

Workflows are scoped per agent. executeWorkflow posts to /api/v1/agents/:agentId/workflows/:workflowId/execute and stores the resulting execution state keyed by run id. Pause and resume actions map to the workflow engine's lifecycle.

typescript 
const runId = await useAdvancedAgentStore.getState().executeWorkflow(
  agentId,
  workflowId,
  { ticketId: 'T-1234', sentiment: 'negative' }

const execution = useAdvancedAgentStore.getState().workflowExecutions[runId];

Capstone: design a support-triage graph

Build a workflow in the Allternit Workflow Engine that triages incoming support tickets. Your graph must demonstrate routing, chaining, and parallelization:

1. Route

Use a condition:if node to branch negative-sentiment tickets to escalation and others to drafting.

2. Chain

On the drafting branch, chain a lookup node to a response-generation node before returning a result.

3. Parallelize

On the escalation branch, run a sentiment analysis and an urgency check in parallel, then merge.

4. Integrate

Wire the workflow into the advanced agent store so it can be triggered from the platform UI.
