Module 2: Prompt Engineering & Evaluation

Learn how Allternit turns vague model requests into reliable, measurable agent behavior using structured prompts, strict schemas, and repeatable evaluation loops.

5 lessons · ~45 minutes Source: surfaces/ai.allternit.com/src/lib/agents

Why prompts are contracts

A prompt is not a wish. In production it is a contract between the operator, the model, and the downstream code that consumes the output. If the contract is ambiguous, every integration downstream pays the cost in parsing logic, retries, and human review.

The Allternit platform encodes this idea in agent-mode-contracts.ts. Every canonical mode—research, code, docs, data, slides, image, video, swarms—declares a required artifact kind, required capabilities, required evidence, and a system prompt. The system prompt itself is the first half of the contract; the validation function is the second half.

  • Be explicit about the output shape. Tell the model whether to return prose, JSON, CSV, HTML, or an artifact manifest.
  • Give the model a role and constraints. The support triage playbook starts with a role ("You are a support triage assistant") and hard constraints (do not draft a response when escalation is true).
  • Provide examples at the boundary. Show the model what near-miss and success look like for the trickiest cases.

Contract principle: The system prompt sets expectations; the JSON Schema enforces structure; the evaluation loop proves the prompt actually meets the contract.

Playbook pattern: support triage

The support triage playbook in docs/public/guides/use-case-playbooks.md demonstrates the classic classification pattern. The prompt asks for a fixed category enum, a sentiment enum, an escalation boolean, and a response string. The evaluation checklist then checks category accuracy, suppression of drafted responses when escalation is true, and brand tone.

Strict schema thinking

Every output the model produces eventually becomes input to some other function. The Tool Belt in docs/public/guides/build-a-tool.md makes this explicit: a tool needs a name, description, JSON Schema input, and an execute function. When a tool is registered with strict: true, the schema is closed—unknown keys are rejected before execution.

The same discipline applies to prompt outputs. If you ask the model to return JSON, the schema should be as strict as a tool input schema. That means:

  • Define required fields. Missing fields should fail validation, not silently default to undefined.
  • Use enums for categorical values. Categories like "Billing" or "Technical" should not be free-form strings.
  • Choose numeric types intentionally. A total that must be a number should never be parsed as a string.
  • Reject additional properties. A closed schema prevents the model from inventing fields that downstream code does not expect.
typescript 
import { ToolRegistry } from '@allternit/sdk/ai-runtime/tools';

const registry = new ToolRegistry();
registry.registerTool(weatherTool, { namespace: 'demo', strict: true });

// Rejected before execute is called
const invalid = registry.validateInput('demo.weather', {
  city: 'Austin',
  timezone: 'CDT'
});
console.log(invalid.errors); // => ["$.timezone is not allowed"]

From tool schema to prompt schema

A prompt that emits JSON is just a tool whose caller is the model and whose consumer is your code. Treat it the same way: namespace it, version it, validate it, and snapshot it. The agent.service.ts create path normalizes agent input, persists allowed tools and skills, and validates the shape with Zod before sending it to the registry API.

Allternit pattern: Tool Belt schemas and prompt output schemas share the same ToolDefinition shape. A capability documented once can be exposed to the model, to an MCP client, or to a prompt's response_format.

The evaluation loop

Prompt engineering without measurement is just taste. The Allternit lifecycle guide shows how agents move from draft to deployment; the same loop applies to prompts. You draft, structure, run against a labeled test set, grade against criteria, iterate, and only then register the agent for production.

Building a test harness

A good prompt evaluation harness has three parts:

  1. A labeled dataset. Each example has inputs and the expected output or pass/fail rule. For triage, that means ticket text plus expected category and escalation.
  2. A grader. The grader compares model output to the label using exact match for enums, regex or semantic checks for text, and schema validation for JSON.
  3. A regression tracker. Each prompt version is run against the same dataset so you can see what improved and what broke.
typescript 
interface TriageExample {
  ticket: string;
  expected: {
    category: 'Billing' | 'Technical' | 'Account' | 'Feature Request';
    escalate: boolean;
  };
}

function grade(output: unknown, label: TriageExample['expected']) {
  const parsed = triageSchema.safeParse(output);
  if (!parsed.success) return { pass: false, reason: 'schema' };
  if (parsed.data.escalate !== label.escalate) return { pass: false, reason: 'escalation' };
  if (parsed.data.category !== label.category) return { pass: false, reason: 'category' };
  if (parsed.data.escalate && parsed.data.response) return { pass: false, reason: 'response-while-escalated' };
  return { pass: true };
}

Observing real runs

The agent lifecycle streams run events through a session. Evaluators can listen for content_block_delta, tool_calls, and usage deltas, then compare them to the expected contract. If a research mode run finishes without citations, the validation layer flags it as invalid before the user sees the answer.

Goal: Every prompt change is backed by a failing test that turns green. No prompt ships on vibe alone.

Capstone: Build a graded prompt for an Allternit agent

Design, implement, and evaluate a prompt that an Allternit agent can run in one of the canonical modes. Your deliverable is a tested prompt package ready for the agent registry.

Choose a mode

Pick one of research, docs, data, or code from agent-mode-contracts.ts. Read its required capabilities and evidence.

Draft the system prompt

Include the role, output format, constraints, and at least one example of a near-miss case.

Define the schema

Write a closed JSON Schema or tool input schema that the output must satisfy. Map it to a response_format or Tool Belt registration.

Evaluate and iterate

Build a labeled dataset of at least 10 cases, run the prompt, and report accuracy plus one concrete change driven by the failures.

Deliverable: A TypeScript file that exports the prompt, schema, grader, and a summary of evaluation results. Include a command that runs the evaluation against the Allternit API.
