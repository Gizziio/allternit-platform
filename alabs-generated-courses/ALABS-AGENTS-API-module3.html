Module 3: Tool Use & the Agent Loop

Learn how Allternit agents decide when to call tools, how the Tool Registry and MCP surface those tools, and how the session event stream captures every turn of the loop.

5 lessons · ~45 minutes Source: surfaces/ai.allternit.com/src/lib/agents

The agent loop

A model running by itself can only produce text. A useful agent can act. The difference is the loop: the model proposes a tool call, the runtime executes it, the result returns to the model, and the model decides what to do next. The loop continues until the task is done or a budget limit is reached.

Inside Allternit, the loop is implemented by agent-mode-executor.ts. It starts with a user prompt and a canonical mode, looks up the mode contract, dispatches to the right plugin or inline handler, and emits the resulting artifact.

  • Prompt + contract. The system prompt and required capabilities come from agent-mode-contracts.ts.
  • Tool calls. The model can request tools from the active registry; the runtime executes them and returns results.
  • Evidence validation. After the run, validateAgentModeExecution checks that the required artifact and markers are present.

Tool Registry and MCP

Tools are not hard-coded into the agent. They live in a ToolRegistry that can hold native platform tools, custom tools, and tools imported from external MCP servers. The registry enforces schemas, namespaces names, and can defer heavy tools until the model explicitly activates them.

typescript 
import { ToolRegistry } from '@allternit/sdk/ai-runtime/tools';

const registry = new ToolRegistry();
registry.registerTool(weatherTool, { namespace: 'demo', strict: true });

console.log(registry.getTool('demo.weather'));
// => { name: 'demo.weather', input_schema: ..., execute: ... }

Attaching an MCP server

The platform can consume external MCP servers through NativeToolBelt.attachMcpServer. Each discovered tool is registered under a namespace with strict: true, so the model sees a closed schema and the runtime can proxy calls back to the server.

typescript 
const belt = new NativeToolBelt(registry);
const names = await belt.attachMcpServer({
  serverId: 'docs',
  listTools: async () => [{
    name: 'read',
    description: 'Read a document',
    inputSchema: {
      type: 'object',
      properties: { id: { type: 'string' } },
      required: ['id']
    }
  }],
  callTool: async (name, args) => {
    return { content: `Read ${name} with ${JSON.stringify(args)}` };
  }
});

console.log(names); // => ['docs.read']

The Rust API also exposes the platform's own registry as an MCP server at /mcp/server, so external clients can call Allternit tools while the platform can call theirs. Both directions share the same tool definitions.

Namespace rule: Names follow ^[A-Za-z][A-Za-z0-9_-]*$. The qualified name becomes namespace.tool, preventing collisions between MCP servers and built-in tools.

Deferred tools

Some tools are expensive or rare. The registry supports deferred tools that are known but not injected into the active schema until the model calls tool_activate. This keeps the context window small and the schema focused.

typescript 
registry.registerDeferredTool({
  id: 'db-tool',
  name: 'query_db',
  description: 'Run a read-only SQL query',
  input_schema: {
    type: 'object',
    properties: { query: { type: 'string' } },
    required: ['query']
  },
  tags: ['database', 'sql']
});

registry.activateTool('db-tool');
console.log(registry.getActiveTools().map(t => t.name));
// => [..., 'query_db']

Sessions and events

The agent lifecycle guide shows how runs are anchored to sessions. A session has a budget—max tokens, turns, and tool calls—and receives a stream of events. The runtime appends events such as content_block_delta, tool_calls, and usage updates, while clients listen over SSE.

This event model is what makes the loop observable. A parent orchestrator can interrupt the session, a human reviewer can watch progress, and an evaluator can reconstruct exactly which tools were called and when.

bash 
curl -N "http://localhost:8013/api/v1/beta/sessions/$SESSION_ID/events" \
  -H "Authorization: Bearer $CLERK_JWT" \
  -H "Accept: text/event-stream"

Budget and interruption

The session budget is created with the session and updated as the run consumes tokens and tool calls. If a human or parent agent needs to stop the run, an interrupt is appended as a user_interrupt event. The loop checks its abort signal and exits cleanly.

Loop invariant: Every tool call is observable, every result is logged, and every completion is validated against the mode contract before the artifact is shown to the user.

Capstone: Add a custom tool to the agent loop

Extend the Allternit agent loop with a custom capability. Your tool should be registered, called by an agent mode, and validated at the end of the run.

Define the tool

Write a ToolDefinition with a strict input schema and an execute function that returns useful data.

Register it

Add the tool to a ToolRegistry under a namespace. Confirm it appears in getActiveTools().

Invoke from a mode

Choose a canonical mode whose contract includes the capability your tool provides, and trace how the executor would call it.

Validate evidence

Show how validateAgentModeExecution would pass or fail depending on whether the tool was actually called and the required artifact produced.

Deliverable: A TypeScript module that exports the tool, a short test that calls it through the registry, and a note explaining which mode contract it satisfies.
