Module 5: Bridge: Admin Runbooks

This bridge module ties together everything from the Cowork course into repeatable admin runbooks. You will learn how to diagnose the gizzi-code CLI, inspect configuration and auth state, read metrics and logs, and use audit and compliance endpoints.

5 lessons · ~45 minutes Source: packages/@allternit/cowork-engine, cmd/gizzi-code

The diagnostics funnel

Most production issues fall into three buckets: authentication, configuration, or observability. The CLI exposes a small set of commands that narrow the bucket quickly.

SymptomCommandWhat it reveals
Cannot connectgizzi auth statusOAuth, API key, or unauthenticated
Wrong settingsgizzi config showMerged effective config
Setting ignoredgizzi config list --sourcesWhich files were loaded and in what order
Slow or failing requestsgizzi metricsRequest counts, latency, tool approvals, timeouts
Crash or odd behavior~/.gizzi/logs/gizzi-*.logStructured runtime logs and crash reports

Config precedence: user defaults → named profile → project overrides → CLI flags. If a setting looks wrong, always check which sources contributed to it before editing files.

Runbook flow

A good runbook starts with the symptom, asks one binary question at a time, and ends with either a fix or a support handoff. The Mermaid diagram below shows the standard flow for Cowork and gizzi-code incidents.

    A[Operator sees issue] --> B{Is it auth?}
    B -->|Yes| C[gizzi auth status]
    B -->|No| D{Is it config?}
    D -->|Yes| E[gizzi config show]
    D -->|No| F{Is it performance?}
    F -->|Yes| G[gizzi metrics / otel]
    F -->|No| H[Collect logs]
    C --> I{Resolved?}
    E --> I
    G --> I
    H --> J[Open support ticket]
    I -->|Yes| K[Document fix]
    I -->|No| H

Auth runbook

  1. Run gizzi auth status. If unauthenticated, re-run gizzi auth login or pre-seed an API-key profile for headless use.
  2. Verify the active profile with gizzi auth profile list.
  3. For CI, prefer API-key auth and store the key in a secret manager, never in the repository.

Config runbook

  1. Run gizzi config path to see the resolved user data root.
  2. Run gizzi config show for the merged effective config.
  3. Run gizzi config list --sources to confirm which files were loaded.
  4. Compare the active profile with gizzi config permission-profiles active.

Observability runbook

  1. Check metrics with gizzi metrics --last-hour for request volume, latency, and timeout rate.
  2. Enable OpenTelemetry spans via experimental.openTelemetry = true or GIZZI_EXPERIMENTAL_OPEN_TELEMETRY=true.
  3. Inspect structured logs under ~/.gizzi/logs/ or the XDG state path on Linux.
  4. Disable telemetry in regulated environments with DISABLE_TELEMETRY=1.

Audit and compliance for admins

The audit feed is an append-only log of organization-scoped events. Admins can write events explicitly and list events with cursor-based pagination. Compliance endpoints let admins export or delete workspace, chat, and artifact data.

bash
curl -s "${ALLTERNIT_API_URL}/api/v1/admin/audit?limit=50" \
  -H "Authorization: Bearer ${CLERK_JWT}"

Common admin actions to monitor include user.login, workspace.create, rbac_role.update, external_key.validate, vault.credential.revoke, and compliance.request.create.

Capstone: Write a Cowork incident runbook

Pick the three most common support tickets your team expects (for example: "Cowork cannot write files", "requests are timing out", "wrong model is selected"). For each ticket, write a short runbook with the exact gizzi or allternit admin commands, the expected output, and the escalation path.

Symptom

One sentence describing the user-visible problem.

Commands

Exact diagnostics commands and flags.

Expected output

What you expect to see when healthy.

Escalation

When to hand off and what data to attach.
