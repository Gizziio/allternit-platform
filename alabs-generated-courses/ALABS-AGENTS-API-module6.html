Allternit Computer Interface (ACI)

The Allternit Computer Interface lets an agent observe and control a computer through a live screenshot stream, mouse and keyboard actions, and human-in-the-loop approvals. Unlike managed cloud sandboxes, ACI can run on the user's own machine, a private VPS, or a self-managed WebVM. Screenshots, credentials, and code stay on infrastructure the customer controls.

ACI routes requests through the Allternit Computer Use gateway and surfaces run state to web, desktop, iOS, and API clients. A browser run starts with a natural-language goal and streams events over SSE at /api/aci/stream/{sessionId}.

  • Self-hosted or private. Data residency stays with the operator; the agent operates on the same network as the host.
  • Approval-first actions. Destructive or high-risk actions pause for human approval before execution.
  • Cross-surface handoff. A run can start on a desktop surface and continue on a paired mobile or browser extension surface.

Design principle: ACI is for users who want agentic browser automation on infrastructure they control, with the same identity and session model as the rest of the platform.

Vision coordinates

ACI uses absolute pixel coordinates for mouse actions. The capability metadata advertises display size, and the UI overlays action bounding boxes scaled from the natural screenshot resolution to the viewport. A coordinate of { x: 640, y: 360 } always points to the center of a 1280x720 display regardless of how the image is rendered.

The computer-use protocol

Every ACI run is governed by a typed protocol in @allternit/computer-use-protocol. The schemas define sessions, devices, observations, actions, approvals, and events so that web surfaces, desktop agents, and headless runners can interoperate without vendor lock-in.

Key abstractions include:

  • SessionSpec. Identifies the run's session, account, conversation, surface, and provider.
  • BrowserRun. Tracks the objective, state, provider, and sequence counters for a run.
  • BrowserObservation. Captures the DOM, accessibility tree, screenshot, or hybrid view of a page with artifact refs and redactions.
  • ActionIntent. A planned action such as navigate, click, type, or screenshot with a reason and optional target ref.
typescript 
const action: ActionIntent = {
  schemaVersion: COMPUTER_USE_PROTOCOL_VERSION,
  actionId: 'act_01J4...',
  runId: 'run_01J4...',
  sessionId: 'sess_01J4...',
  kind: 'click',
  reason: 'Submit the login form',
  targetRef: 'ref-login-button',
  input: {},
};

const observation = await provider.observe(sessionId);
const events = await provider.execute(action);

Run states and action states

A run moves through queued → running → approval_pending → completed/failed/cancelled. Each action has its own lifecycle: planned → resolved → policy_checked → approval_pending → executing → observed → verified → committed. The policy engine can allow, deny, or require_approval based on action kind and risk.

Safety first: The requiresApprovalFor list in a workflow spec explicitly names action kinds that must stop for human review.

Headless execution with gizzi-code

Not every automation task needs a browser. The gizzi-code CLI provides a headless execution context for local files, shell commands, and repository operations. gizzi exec is a pipe-safe alias for gizzi run that prints the response and exits without launching the TUI.

Headless mode is ideal for CI scripts, pre-commit hooks, and autonomous agents that need deterministic output:

  • gizzi exec "Summarize README.md" runs a single prompt and returns text.
  • git diff | gizzi exec pipes a diff into the agent for review.
  • gizzi exec --output-format stream-json emits a JSON event stream for automation.
bash 
# Headless commit-message generation
git diff --cached | gizzi exec \
  "Write a conventional commit message for the staged changes"

# JSON event stream for a downstream parser
gizzi exec --output-format stream-json \
  "List the top three risks in this API spec"

Under the hood, exec sets --print, defaults output format to text, and uses the dontAsk permission mode so it can run unattended. Permission profiles in config.toml can still enforce rules such as bash=ask or edit=ask when needed.

Autonomous Code Factory

The Autonomous Code Factory view in the platform surfaces four governance pillars that turn raw code generation into a self-improving, reviewable pipeline:

  • RiskPolicy. Classifies every proposed change by risk tier so that low-risk fixes can flow quickly and high-risk changes get mandatory review.
  • Evidence Validation. Binds artifacts to SHA-bound evidence so the factory can prove what code was produced, what tests ran, and what changed.
  • Merge Governance. Applies risk-tiered auto-merge rules: green CI plus low risk may merge automatically, while medium or high risk requires human sign-off.
  • Remediation Loop. Applies deterministic patches, reruns validation, and escalates only when the loop cannot resolve a failure.

Factory contract: Every autonomous change must carry a risk classification, evidence artifacts, and a merge decision before it reaches the main branch.

When to combine ACI and the factory

Autonomous coding does not stop at file edits. An agent may need to open a browser to read API docs, file a pull request, or verify a deployed service. ACI gives the factory eyes and hands; the factory gives ACI governance and reproducibility. Together they form a closed loop: observe, plan, act, validate, merge.

typescript 
// Simplified autonomous change flow
const proposal = await factory.plan({
  objective: 'Add retry middleware to the LLM gateway',
  sourceFiles: ['cmd/allternit-api/src/llm_gateway/proxy.rs'],
});

const risk = await riskPolicy.classify(proposal);
const evidence = await validation.run(proposal.tests);
const decision = await mergeGovernance.decide(risk, evidence);

if (decision === 'auto_merge') {
  await proposal.apply();
} else {
  await reviewQueue.submit(proposal, risk, evidence);
}

Capstone: Build a supervised browser-to-code workflow

Combine ACI, the computer-use protocol, and the Autonomous Code Factory in a single end-to-end task.

Goal

Use ACI to navigate an internal API docs page, extract an endpoint schema, then generate a typed client function.

Constraints

Require approval for navigate and download. Cap the run at 50 turns. Run validation tests before merge.

Deliverable

A BrowserWorkflowSpec JSON, the generated client code, and a risk/evidence report produced by the factory.
