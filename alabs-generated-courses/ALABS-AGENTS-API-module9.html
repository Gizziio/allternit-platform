Module 9: Engineering: Harness

Learn how Allternit unifies model execution behind a single harness and API gateway, turning provider differences, retries, fallbacks, and quotas into a predictable execution layer.

6 lessons · ~45 minutes Source: sdk/allternit-sdk/src/ai-runtime/harness

Why a harness?

Every provider exposes a different HTTP surface, authentication scheme, chunk shape, and error vocabulary. Production code that calls these surfaces directly becomes a tangle of provider-specific branching. The Allternit harness is the unified execution layer that absorbs those differences.

AllternitHarness in sdk/allternit-sdk/src/ai-runtime/harness/index.ts exposes three entry points:

  • stream() — returns an async generator of normalized chunks such as text, tool_call, citation, and done.
  • complete() — collects the stream into a single string.
  • run() — collects the stream into a HarnessResponse that preserves usage, citations, and stop reason.

One contract, many runtimes. The harness is where provider-specific protocols are normalized into provider-agnostic events.

Execution modes

The harness supports four modes, validated at construction time:

ModeRequired configUse case
byokAt least one provider API keyUse your own provider keys
cloudbaseURL + accessTokenAllternit managed cloud
localbaseURLLocal model server such as Ollama
subprocesscommandCustom model runner

import { AllternitHarness } from '@allternit/sdk';

const harness = new AllternitHarness({
  mode: 'byok',
  byok: {
    openai: { apiKey: process.env.OPENAI_API_KEY! },
  },

  provider: 'openai',
  model: 'gpt-4o',

Middleware: retries, fallbacks, and observability

Middleware in the harness is a stack of hooks that runs on every request. middleware.ts defines three hook types:

  • beforeRequest — mutate or log the request after validation but before system/provider prompt injection.
  • afterResponse — transform the collected response before run() returns it.
  • onError — recover from a thrown error by yielding a replacement stream.

The default harness installs two built-in middlewares automatically:

  • Refusal fallback — when fallbackModels are configured, a provider refusal or content-filter error re-routes the request to the next model.
  • Retry — network errors, timeouts, rate limits, and retryable HTTP statuses are retried with exponential backoff and jitter.
typescript 
const harness = new AllternitHarness({
  mode: 'byok',
  byok: {
    openai: { apiKey: process.env.OPENAI_API_KEY! },
    google: { apiKey: process.env.GOOGLE_API_KEY! },
  },
  fallbackModels: [
    { provider: 'openai', model: 'gpt-4o-mini' },
    { provider: 'google', model: 'gemini-1.5-flash' },
  ],
  retry: { maxRetries: 3, initialDelayMs: 500, jitter: true },
  middleware: {
    beforeRequest: async (req) => {
      console.log('[harness] routing', req.provider, req.model);
      return req;
    },
    afterResponse: async (res) => {
      console.log('[harness] tokens', res.usage?.totalTokens);
      return res;
    },
  },
});

Order matters. Refusal fallback is installed first so it can intercept content-filter errors before the retry middleware consumes a retry attempt on the same model.

The API gateway

While the SDK harness runs inside your process, the Allternit API gateway (cmd/allternit-api/src/llm_gateway) is the server-side counterpart. It exposes an OpenAI-compatible surface at /v1, validates virtual-key authentication, applies routing policy, meters usage, and persists events.

B5 routing policy

Callers can pass a policy alias instead of a concrete model. The gateway's B5 router resolves the alias to a winner model plus a cross-provider fallback chain:

  • auto / allternit-balanced — equal weight across benchmarks.
  • allternit-code — weights coding benchmarks heavily.
  • allternit-reasoning — weights reasoning benchmarks heavily.
  • allternit-knowledge — weights knowledge benchmarks heavily.
  • allternit-instruct — weights instruction-following benchmarks heavily.

Scoring is deterministic: total = 0.75 × quality + 0.25 × cost_efficiency. Fallbacks are always from distinct providers to maximize resilience.

Idempotency, batches, and rate limits

Production workloads need more than streaming. The gateway adds three operational controls:

Idempotency

Non-streaming POST /v1/chat/completions honors an Idempotency-Key header. Duplicate keys for completed requests replay the stored response; duplicates for in-flight requests return 409 Conflict with code allternit.idempotency_conflict. Streaming requests cannot be replayed, so the header is ignored when stream: true.

Batches

POST /v1/batches stores a batch of completion requests and runs them asynchronously. Each request is validated against the key's model allowlist. The worker submits to the provider batch endpoint, polls to completion, and stores results behind GET /v1/batches/:id/results.

Rate limits

GET /v1/rate-limits returns the caller's sliding-window request quota and token budget. Requests are counted per minute; tokens are drawn from the key's monthly budget and any tenant hard cap, with the tighter remaining value winning.

curl -s "$ALLTERNIT_API_URL/v1/batches" \
  -H "Authorization: Bearer $ALLTERNIT_API_KEY" \
  -H "Content-Type: application/json" \

    "requests": [

2. Add middleware
