Module 1: Messages, Streaming, and Provider Adapters

Learn how Allternit turns any AI SDK provider stream into a single, predictable event vocabulary using the provider-adapter layer.

6 lessons · ~45 minutes Source: @allternit/provider-adapters

Why provider adapters?

Every AI provider speaks a slightly different dialect. Different AI providers and local models all return streaming responses, but the shape of each chunk, the lifecycle events, and the error payloads differ. The Allternit platform does not hard-code against any one provider. Instead, it normalizes every stream into a single ReplyEvent contract.

That normalization lives in @allternit/provider-adapters. The AiSdkReplyAdapter consumes the AI SDK's fullStream and emits canonical events such as reply.started, reply.item.added, reply.text.delta, and reply.completed. Downstream surfaces—chat transcripts, agent runners, and canvas artifacts—only need to understand one schema.

  • Swap providers without rewriting UI code. The adapter hides provider-specific chunk shapes.
  • Get streaming, reasoning, tool calls, and citations through one async iterator.
  • Route failures consistently. Provider errors and aborts become reply.failed events.

Adapter pattern: one canonical event contract, many providers. The adapter is the bridge between the AI SDK and the rest of Allternit.

Your first request

Start with a plain AI SDK streamText call, then wrap it with AiSdkReplyAdapter. The adapter needs a replyId, a runId, and an onEvent callback. Every event it emits carries those IDs so the rest of the platform can correlate it with the right conversation and run.

typescript
import { streamText } from "ai";
import { AiSdkReplyAdapter } from "@allternit/provider-adapters";

// aiSdkProvider = any AI SDK-compatible model factory you configure
const result = streamText({
  model: aiSdkProvider("model-id"),
  messages: [{ role: "user", content: "Explain provider adapters in one paragraph." }],
});

const adapter = new AiSdkReplyAdapter({
  replyId: "msg_01",
  runId: "run_01",
  onEvent: (event) => console.log(event.type, event),
});

await adapter.consume(result.fullStream);

The consume method loops over every part in fullStream, calls process(part), and catches uncaught errors so they surface as reply.failed instead of crashing the runner.

Streaming responses

Watch a recorded terminal session that shows the adapter emitting lifecycle events as a real agent run completes.

As the model generates tokens, the adapter emits a strict lifecycle. Learn these four events and you can render any streaming reply in Allternit.

EventWhen it firesWhat to render
reply.startedFirst stream part arrivesShow the assistant message shell and a typing indicator.
reply.item.addedA new text, reasoning, tool-call, or artifact item opensAllocate a slot in the transcript for that item kind.
reply.text.deltaEach text token arrivesAppend the token to the active text item.
reply.completedStream finishes cleanlyHide the indicator and mark the reply done.

Beyond text, the same lifecycle covers reasoning blocks (reply.reasoning.delta), tool calls (tool_call.started, tool_call.progress, tool_call.completed), file artifacts (artifact.created), and citations (citation.added). The adapter also extracts <thinking> tags from providers that do not emit native reasoning events.

Key takeaway: Write your UI against reply.* events, not against provider SDK shapes. A new provider only needs a new adapter instance.

Choosing a model

Allternit can route the same request to many models through the AI SDK. Picking the right model is a trade-off between latency, cost, and capability. The adapter makes these swaps one-line changes.

ProfileTypical use caseCharacteristics
Fast / cheapClassification, routing, summariesLow latency, lower cost, acceptable for narrow tasks.
BalancedGeneral chat, multi-turn contextGood reasoning and instruction following at moderate cost.
Capable / expensiveComplex reasoning, coding, analysisHighest quality, slower, priced per token.
Tool-capableAgent loops with function callingReliable structured JSON and parallel tool calls.

Because the adapter is provider-agnostic, you can run an experiment across providers simply by changing the model argument in streamText. The transcript, token accounting, and error handling stay the same.

Capstone: Build a provider-agnostic chat runner

Put the module into practice. Create a tiny TypeScript runner that accepts a provider name and a user message, calls streamText with the matching model, and pipes the result through AiSdkReplyAdapter.

Step 1 — Wire the model

Map a provider argument (provider-a, provider-b, local) to an AI SDK model factory and a model identifier.

Step 2 — Stream through the adapter

Instantiate AiSdkReplyAdapter with a fresh replyId and runId, then call consume(result.fullStream).

Step 3 — Render events

Print each canonical event type as it arrives. Show reply.started, buffer reply.text.delta tokens, and print reply.completed.

Stretch goal

Switch providers mid-conversation and confirm the event stream shape stays identical. Try enabling a tool and observe tool_call.started events.

Save your runner as src/runners/provider-agnostic.ts and run it with npx tsx against two different providers. If the transcript events match, your adapter integration is working.
