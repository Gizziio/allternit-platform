Module 2: Delegation: Scoping Work for Agents

Learn when to hand work to an agent, how to write a task spec that an executor can actually follow, and how Allternit's agent-definition and orchestration layers keep humans in control.

5 lessons · ~35 minutes Source: .agents/skills/agent-orchestrator

The 4D framework

AI fluency is not about using the biggest model for everything. It is about matching the right surface to the right task. Allternit's curriculum organizes fluency around four Ds:

  • Decide — Should a human do this, or can an agent help?
  • Delegate — If an agent should help, which surface and what scope?
  • Describe — Write the prompt or task spec so the agent can succeed.
  • Discern — Review the output before accepting it as truth.

This module focuses on Delegate. Delegation fails when the task is either too vague or too risky to verify. The goal is to scope work so the human stays in control while the agent does the mechanical part.

Delegation rule: Only delegate what you can verify. If you cannot check the result, keep the human in the loop.

Scoping a delegated task

The CLI Agent Orchestrator skill breaks delegation into six phases. The first two—Scope and Plan—are the human's job. The executor does the work, but the human must define success before any code is written.

  1. Detect — Confirm that at least one executor CLI and tmux are available.
  2. Scope and Plan — Do the analysis yourself, write a spec/map doc, and write a one-phase task spec with exact file paths and constraints.
  3. Spawn — Create an isolated worktree and start the executor in its own session.
  4. Send and Monitor — Give the executor the task file and watch for a sentinel file.
  5. Review — Check the true footprint, verify claims in code, run a cheap syntax gate, and send failures back.
  6. Iterate — Write the next phase's spec and repeat until done.
markdown 
## Phase 1 — Extract payment hook

### Scope
- Refactor `src/features/payment/usePayment.ts` so card-token logic lives in a new `useCardToken.ts` hook.
- Update callers in `Checkout.tsx` and `PaymentModal.tsx`.
- Do NOT touch server routes or database models.

### Constraints
- No builds or dev servers.
- Match existing hook idioms and error handling.
- Keep the diff under 150 lines.

### Deliverable sentinel
When finished, write `docs/PAYMENT_HOOK_PHASE_1_NOTES.md` starting with YAML frontmatter:
- status: done|blocked
- files_changed: [list]
- deviations: [what + why]

Task scoping checklist

Before spawning an executor, answer these questions:

  • Can I state the desired outcome in one sentence?
  • Do I know which files should change and which must not?
  • Can I verify the result without running a full production system?
  • Is the work small enough to review in a few file reads?
  • Do I have a sentinel that proves the task is complete?

Good spec: "Refactor the payment hook, update two callers, keep under 150 lines, and write a NOTES file." A bad spec is "make the payment flow better."

Defining the agent

Delegation is not only about external executors. Inside the Allternit platform, agents are defined through agent-definition.ts. The defineAgent factory turns a compact declarative definition into a validated CreateAgentInput.

typescript 
import { defineAgent } from '@/lib/agents/agent-definition';

const paymentRefactorAgent = defineAgent({
  name: 'payment-refactor-agent',
  description: 'Refactors payment hooks while preserving existing callers.',
  instructions: 'You are a senior frontend engineer. Prefer small, testable hooks. Never change server routes.',
  capabilities: ['file_write', 'code_execution'],
  character: {
    specialtySkills: ['react', 'refactoring'],
    temperament: 'balanced',
  },
});

console.log(paymentRefactorAgent.characterLayer.roleCard.outputs);
// => []

The factory fills in canonical defaults for model, provider, harness, surfaces, trust tier, and write scope. It then validates the result with Zod and, by default, enforces the agent creation checklist. This means any agent created programmatically satisfies the same bar as one created through the UI form.

Lifecycle and deployment

Once an agent is defined, the lifecycle guide shows how to create it, bind it to a session with a budget, stream events, interrupt if needed, and deploy on a cron schedule. The budget fields—max_tokens, max_turns, and max_tool_calls—are the guardrails that keep a delegated task from running away.

bash 
curl -s -X POST http://localhost:8013/api/v1/beta/sessions \
  -H "Authorization: Bearer $CLERK_JWT" \
  -H "Content-Type: application/json" \
  -d "{\"agent_id\":\"$AGENT_ID\",\"name\":\"payment-refactor-7\",\"budget\":{\"max_tokens\":10000,\"max_turns\":20,\"max_tool_calls\":50}}"

Capstone: Scope a real task for delegation

Pick a small change in a codebase you know and walk it through the full delegation pipeline. The deliverable is a task spec plus a short reflection.

Decide

State the task in one sentence and explain why it is a good candidate for delegation.

Scope

List the files that should change, the files that must not, and the success sentinel.

Define the agent

Write a defineAgent call with the right capabilities, instructions, and character for the task.

Plan verification

List three concrete checks you would perform in the Review phase before accepting the work.

Deliverable: A markdown task spec file and a short TypeScript snippet defining the agent. Include your 4D reflection: why delegate, what you kept human, and how you will verify the result.
