Module 8: Bridge: Production Deployment

Learn how to deploy Allternit agents at scale: OpenAI-compatible API semantics, rate limits, idempotency, retries, batch jobs, provider failover, and the security controls that guard every request.

6 lessons · ~50 minutes Source: cmd/allternit-api/src/llm_gateway

The public API surface

The public Allternit API is mounted at /v1 and is backed by the Gizzi runtime. It uses virtual-key authentication and returns OpenAI-compatible request and response shapes, with Allternit-specific error codes such as allternit.rate_limited, allternit.budget_exceeded, and allternit.idempotency_conflict.

Rate limits and budgets

GET /v1/rate-limits returns the caller's sliding-window request rate and token budget. Requests are capped per minute; tokens are capped monthly or by a tenant hard cap, whichever is tighter. When a limit is exceeded the gateway returns 429 Too Many Requests with code allternit.rate_limited or allternit.budget_exceeded.

bash 
curl -s "$ALLTERNIT_API_URL/rate-limits" \
  -H "Authorization: Bearer $ALLTERNIT_API_KEY"

Idempotency

The gateway honors Idempotency-Key for non-streaming POST /v1/chat/completions only. Streaming requests cannot be replayed from a stored body, so the header is ignored when stream: true.

  • The key must be 1–255 ASCII characters.
  • A duplicate key for a completed request replays the stored body with 200 OK.
  • A duplicate key for an in-flight request returns 409 Conflict with allternit.idempotency_conflict.
  • An in_progress row older than 10 minutes is treated as abandoned and may be retried.

Batches

POST /v1/batches stores a collection of chat-completion requests for asynchronous execution. The worker validates each request, checks it against the key's model allowlist, posts to the provider batch endpoint, and polls to completion. Status flows validating → in_progress → completed/failed/cancelled. Results are retrieved with GET /v1/batches/:id/results.

Operational note: Use idempotency for synchronous retries, batches for offline throughput, and rate-limit headers for client-side pacing.

Provider registry and failover

Provider metadata lives in two places: the TypeScript SDK's PROVIDER_REGISTRY and the API's GET /v1/models endpoint, enriched with limits from the Gizzi provider catalog. Each entry carries feature flags, default model, supported models, and API-key requirements.

Policy aliases and routing

The caller can pass a concrete provider/model id or a policy alias such as auto, allternit-balanced, allternit-code, allternit-reasoning, allternit-knowledge, or allternit-instruct. Aliases are owned by Allternit and resolved at request time by the B5 router, which scores the connected provider catalog and derives a primary model plus a fallback chain.

Retry/failover engine

The failover.rs module decides when a failed or refused completion should be retried, how long to back off, and which model to try next. It is intentionally kept pure so the policy rules can be unit-tested without a live runtime.

  • Retry policy is loaded per organization from fallback_retry_policies. Defaults include max 2 retries, exponential backoff from 500ms to 8000ms, and full jitter.
  • Retryable statuses include refusal, error, rate_limited, and timeout.
  • Fallback chain sends the top distinct-provider candidates to Gizzi as fallbackModels.

Security model

Allternit uses two authentication modes. Clerk JWTs protect the web/desktop UI and admin APIs, scoping sessions to organization and role. Virtual LLM keys (ak-…) protect the /v1 surface; each key is tied to an organization, optional model allowlist, monthly budget, and rate limit.

Authorization and data protection

  • RBAC. Owners and admins manage workspaces, keys, budgets, DLP rules, and analytics. Members are restricted to permitted resources.
  • Model allowlists. Virtual keys can be restricted to specific models or aliases, preventing calls to unapproved providers.
  • Workspace isolation. Agents, sessions, files, and memory are scoped to an organization and, where applicable, to individual users.
  • Encryption. All traffic uses TLS. SQLite databases and vault stores encrypt sensitive values; connector tokens and vault entries use a configurable encryption key.

DLP and prompt safety

The LLM gateway scans outgoing requests for secrets, PII, and prompt-injection patterns. Detections can warn, redact, or block. Admin endpoints can score user text against system prompts to detect accidental leakage. Strict tool-use validation closes schemas with additionalProperties: false to reduce injection surface.

Threat mitigation: stolen keys are bounded by rate limits and budgets; secret exfiltration is caught by DLP; provider credentials never reach clients.

Gateway middleware pipeline

Every /v1 request passes through a layered middleware chain before it reaches the Gizzi runtime. The order matters: auth first, then rate limiting, then DLP, then budget pre-check.

LayerResponsibility
idempotency_key_middlewareReject malformed Idempotency-Key headers before spend.
llm_key_middlewareResolve Bearer ak-… to an organization and key context.
rate_limit_middlewareEnforce per-key sliding-window request limits.
dlp_middlewareScan for secrets, PII, and injection patterns.
budget_middlewarePre-check monthly and tenant token budgets.
proxy::chat_completionsResolve model, create Gizzi session, collect events, record usage.

Usage recording

Every completed request writes one llm_usage_events row with tokens, cost, latency, provider, model, fallback history, and routing decision. The gateway recomputes cost server-side from a cached price matrix and flags mismatches greater than 1%. Prometheus counters and histograms are emitted from the same choke point.
