What shipped

This was a light week for merged work — one pull request landed — but it sits on top of a release that went out the day before this log's window opened, so it's worth covering both.

Desktop v1.1.1 is out

On September 9 we published Allternit Desktop v1.1.1. This is the fully bundled build: the platform UI (a Next.js static export), the Rust API backend (local on :8013), and the Gizzi AI runtime (Bun, local on :4096) all ship inside the installer. Once it's installed, nothing needs the network.

  • macOS builds for both arm64 and x64, plus a Windows installer
  • Auto-updates enabled, so existing installs will get prompted when the next build lands

Service worker cache guard

The only merge this week was PR #247 (fix/sw-cache-guard). The name is terse, but the shape of the fix is clear: a guard around the service worker's cache behavior. Service workers sit between the app and the network and decide what gets served from local cache versus fetched fresh — without a guard in the right place, a stale cached response can be served when a fresh one was expected, or the cache can interfere with content that should never have been cached at all.

Given that the desktop app serves a static UI that loads https://ai.allternit.com, cache correctness matters twice over: a stale service worker cache in the desktop shell could pin a user to an old version of the interface even after the API and runtime underneath it have moved forward.

Why it matters

Most of this week's value is in the release, and the release is about a single property: the app works without the internet. That's not a convenience feature for our user base — engineers running local models, people on unreliable connections, anyone who wants the AI runtime on their own machine without a dependency on a hosted service. Bundling all three components (UI, Rust API, Bun runtime) into one installer means the "local" in "local AI" is actually true end to end. The UI talks to a backend on localhost:8013, the runtime on :4096, and nothing leaves the machine unless you tell it to.

The cache guard fits the same theme. Local-first software has a specific failure mode that hosted software doesn't: because everything is expected to work offline and from local resources, stale state is harder to notice and harder to clear. A user on a hosted app refreshes and gets the new build. A user with a desktop app and an aggressive service worker cache might keep running last month's UI against this week's runtime — and the symptoms of that mismatch (subtle, hard to reproduce, "works on my machine" in the worst way) are exactly the kind of bug report that eats an afternoon. Putting a guard around the cache path is cheap insurance against that class of problem.
