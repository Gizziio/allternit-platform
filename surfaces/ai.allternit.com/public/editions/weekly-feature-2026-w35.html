Long-Horizon Agent Memory: From Context Windows to Working Memory

A://SUDO Reality · Weekly Magazine · August 26, 2026

By A://SUDO Reality · research desk

August 26, 2026 · 5 min read

Cover Story

Long-horizon agents are caught in a paradox: they have never been able to remember more, yet they have never been worse at using what they remember. Context windows now swallow 128,000 tokens or more, but new evidence from financial-analysis workflows shows that simply retrieving a risk disclosure from a long filing has almost no effect on an LLM's investment judgment, even when direct retrieval stays accurate. The history is present; it is not operative. That gap is why the architecture of agent memory is being redrawn. The latest work moves the field away from the brute-force model of "read everything" toward a structured working memory that tracks task state and selects skills grounded in the current need.

This is not an incremental tweak to retrieval-augmented generation. It is a response to a specific, expensive failure mode in production agents: as execution histories grow, the task state becomes obscure, and the agent starts invoking the wrong skills at the wrong time. A new recursive Experiential-Working Memory architecture, Recuris, tackles this by coupling a working-memory layer that monitors progress with an experiential-memory layer of skills and past execution traces. A fixed meta-agent then uses structured execution evidence to update only the memory component responsible for a failure, validation-gating each change. The result is an agent that can improve its own skill memory without retraining the underlying model.

The practical signal is already showing up in product form. Anthropic's Claude Cowork is introducing shared memory across chat and Cowork sessions so that users stop re-briefing the assistant. That solves the user-context problem, but the deeper engineering challenge is the same: separate what an agent can read from what it can act on. Recuris and related research point toward a production pattern in which context windows become a transport layer, not a reasoning layer. Working memory becomes the reasoning layer.

For production agents, the problem is no longer how much history the model can read, but how little of the right history it can act on.

For engineering teams, the stakes are clear. If your agent executes multi-step workflows over minutes or hours, the dominant failure mode is no longer "I ran out of context." It is "I lost the thread." Fixing that requires re-architecting memory around task state, not token count. The teams that get this right will build agents that are debuggable, improvable, and economically viable at long horizons. The teams that do not will keep paying for ever-larger context windows and still wonder why their agents make the same mistakes twice.

Technical Breakdown

How it works

At the center of Recuris is a separation of concerns borrowed from cognitive architecture. Instead of feeding the entire execution history into the LLM, the system maintains three memory components:

  1. Experiential Memory — a long-term store of prior trajectories, reusable skills, and raw execution traces.
  2. Working Memory — a compact representation that tracks current task progress and selects skills from Experiential Memory based on present need.
  3. Skill Memory — a validated, executable skill library that the agent actually invokes.

During execution, the agent's Working Memory decides which skill to call. The full history is not re-read; the skill is grounded in the current task state. After each episode, execution traces are turned into structured evidence. A fixed meta-agent diagnoses failures and proposes targeted updates to Skill Memory — or to how Working Memory selects skills. Each proposed update is validation-gated before being committed. The cycle produces new execution evidence, and the process repeats. The result is recursive self-improvement localized to specific memory components.

This design directly addresses the long-context retrieval-integration gap shown by Liu and Liu. In their experiments, when total context grows from 2,000 to 128,000 tokens while focal-firm information is held fixed, direct retrieval of a risk disclosure remains accurate, but its influence on the model's investment judgment falls to the experimental noise floor. The model can read the document; it cannot keep the relevant fact active across the reasoning chain. Working memory is intended to solve exactly that: keep the task-relevant signal active while suppressing irrelevant context.

What problem it actually solves vs. what the marketing claims

Marketing around long context often conflates "can access" with "can use." Recuris does not magically expand the effective horizon of every LLM. It solves a structural problem in long-horizon agent harnesses: skill misalignment caused by history overload. It also provides a failure-attribution mechanism. Because updates are localized and validation-gated, engineers can trace a bad action to a specific memory component rather than debugging an opaque, monolithic prompt.

Limitations and edge cases

The architecture assumes a stable task structure and a reusable skill library. In open-ended domains where skills are not cleanly factorable, Working Memory may select poorly and updates can compound. Validation gating adds safety but can also reject valid updates, slowing learning. The latency cost of the meta-agent update loop is not specified in the available sources. The experiments cover multiple tasks, but real-world multi-hour workflows with human feedback loops remain unverified. There is also no evidence in the sources that Recuris reduces inference cost relative to simpler retrieval patterns; cost depends heavily on implementation and on whether memory maintenance runs synchronously or asynchronously.

Production Implications

When to adopt it, when to wait

If your agent runs tasks with many steps, repeated tool calls, and evolving state, start designing around a working-memory architecture now. If your agent is a single-turn classifier, a short chatbot, or a simple retrieval-and-summarize pipeline, this is overkill.

The immediate move for production teams is to stop treating the context window as a working-memory substitute. Build an explicit task-state object that the agent updates after each step. Add a skill registry with selection logic. Use retrieval to populate context, but separate the active reasoning state from the raw history. Recuris provides a pattern: a meta-agent loop that reviews failures and proposes memory updates only after validation. That adds components — a memory store, a skill registry, an evaluator/validator, and observability into which memory component failed — but it replaces the current regime of endlessly growing prompts and repeated mistakes.

Integration complexity and operational concerns

Integration complexity is high. You will need to instrument execution traces so failures can be localized to Working Memory, Skill Memory, or Experiential Memory. You will need a validation harness; otherwise the meta-agent will corrupt the skill library. Operational concerns include update drift, version control for skills, and latency from the meta-reasoning step. The tradeoff is compute spent on memory maintenance versus model calls saved by better skill selection. In high-frequency, low-latency workflows, the extra reasoning step may be unacceptable. In asynchronous, long-running tasks, it is likely worth it.

Cost and performance tradeoffs

Cost context is changing at the same time. Claude Code costs $20 to $200 per month depending on usage, while open-source alternatives like Goose target the same terminal-agent pattern without a subscription. Meanwhile, OpenAI's Jalapeño custom inference chip is promising faster, more power-efficient inference, which could lower the cost of the meta-agent loop. Anthropic's Claude Cowork shared memory is a consumer-facing signal of the same trend, but it solves user-context persistence, not task-state working memory.

The so what: production AI teams should care because long-horizon reliability is the difference between a demo and a workflow. The winning design is not a bigger prompt; it is a memory architecture that knows what matters now.
